# Glossary

Core concepts used across ai-hats code and docs. One short definition per term, plus a pointer to the canonical detail. **Not** a catalog — for the full listing of roles, skills, traits, or CLI commands use `ai-hats list ...` and `ai-hats --tree`.

This file is the naming source-of-truth. When another doc needs to define a core term, link here instead of redefining it.

---

## Provider

A target LLM CLI that ai-hats wraps. **`provider` is the published word and `Surface` is the code name** (HATS-1826): the CLI flag (`-p/--provider`), the `ai-hats.yaml` key, the `ai_hats.providers` entry-point group and the `provider` marker in session artifacts all keep the published spelling, because renaming them breaks installed third-party surfaces and existing sessions; every Python symbol inside the process says surface — `Surface`, `SurfaceHint`, `ClaudeSurface`, `ai_hats.surface_registry.get_surface`. Do not "fix" one side to match the other without a migration. The set is an **open registry** (HATS-870) — every provider is discovered through the `ai_hats.providers` entry point, whether it ships inside `ai-hats` (`claude`, `agy`, `cline`, `codex`, `opencode`) or in another installed package (see [Surface plugin](#surface-plugin)). The choice lives in `ai-hats.yaml` (`provider:`). A role composition is built per session and delivered per provider from the session cache — see [1] for the per-surface table. Switching keeps composition intact: `ai-hats config set -p <provider>`.

Detail — see [1].

## Surface plugin

A [Provider](#provider) for another agent CLI registered through the `ai_hats.providers` entry point (HATS-870), giving ai-hats a new surface. The entry point is the only seam, so an out-of-tree package can still register one — but the built-in surfaces are **not** separate distributions: each is a folder in the surfaces area (`src/ai_hats/surfaces/<name>/`), declared in the root `pyproject.toml` and shipped inside `ai-hats`, so it arrives with the integrator and nothing installs it. Until HATS-1826 `agy` / `cline` / `codex` / `opencode` were published packages under `packages/surfaces/<name>/`; they paid a distribution's cost without its value, which is the case ADR-0026 D10 refuses. A surface may also ship a `TranscriptParser` that rides the provider (`Surface.transcript_parser`, HATS-948) to normalize its session log into audit + usage; `Surface.resolve_transcript` (HATS-1087) is the matching half — the parser knows HOW to read the log, the resolver knows WHERE it lives. A surface without a structured log overrides neither and falls back to the trace log.

## Session

One invocation of the provider CLI under a chosen role. Entry points: `ai-hats` (no subcommand, or with positional prompt text / provider flags), `ai-hats agent <role>`, `ai-hats execute …`. Per-session artefacts land in `<ai_hats_dir>/sessions/runs/session_<id>/` (`audit.md`, `metrics.json`, `usage.json` — the machine-readable `usage/v1` context-cost report, HATS-664; `transcript.txt`, `meta_prompt.txt` — the exact bytes the provider saw as system-prompt override, HATS-523). The runtime ends a session with a `session_end` event that may trigger a per-session retrospective — see [Reflect](#reflect).

Lifecycle diagram — see [2].

**Measurement flags** — the `flags` vocabulary of a session's `metrics.json` (`audit/v1`), saying why a counter is absent or how it was obtained; shared constants in `ai_hats_observe.artifacts`, so a consumer compares rather than substring-matches prose. `no-structured-transcript` / `sensor-error` / `not-finalized` — the record as a whole is unmeasured (HATS-1374). `token-telemetry-unavailable` — the transcript parsed fine, but the surface emits no usage at all, so only the token counters are withheld (HATS-1397). `token-telemetry-estimated` — the counters exist and nobody measured them: scraped from rendered output or estimated from text length, so they are written *and* marked, and the step that destroys work (`is_zero_output`) refuses to act on them (HATS-1433).

**Parent escape-hatch** — a deterministic way out of a *wedged* interactive (HITL) session. The provider runs under a PTY proxy whose stdin is in raw mode, so Ctrl-C is forwarded to the child as a byte; if the child stops honouring it and never exits, the user is otherwise trapped until an external kill. The runtime counts consecutive Ctrl-C (`0x03`) within a ~1.5 s sliding window: the first two are forwarded unchanged (dormant for healthy sessions, which exit on the second Ctrl-C via master EOF), and the third is intercepted — the parent runs its bounded shutdown and returns exit code **130** (so a wedged session is no longer mis-reported as success). Source: `runtime._scan_escape` + `WrapRunner._pty_spawn` (HATS-679).

**Finalize shield** — the same gesture on the other side of the provider's exit. Once the child is gone the terminal is back in cooked mode, so a stray Ctrl-C arrives at the parent as a real SIGINT and lands inside whichever finalize step is running — costing that step silently (a session lost its retro decision, reviewer spawn, and `retro.log` outright). For the whole finalize window — `_finalize_session_basic`, the `finalize-hitl` / `finalize-subagent` sub-pipeline, the session-end banner — SIGINT is held: each press prints one line and is dropped, and the third inside the ~1.5 s window raises `FinalizeAborted` (deliberately not `Exception` / `KeyboardInterrupt`, both of which the per-phase HATS-086 catches would swallow), abandoning the remaining work with exit **130** while the session id still reaches stdout. Counting is shared with the parent escape-hatch (`runtime._press_trips`). Source: `runtime.sigint_shield` (HATS-1426).

## Library layer

One of the three tiers the shipped library is split into. All three load at every session, lowest priority first — `core` → `usage` → `ai-hats-dev` — and a later layer wins a name it shares with an earlier one; your own roots (`~/.ai-hats/`, `<project>/libraries/`) sit above all three by the same rule.

| Layer         | Holds                                                                             | Required for a library root |
| ------------- | --------------------------------------------------------------------------------- | --------------------------- |
| `core`        | engine fundament — without it `init` / `self init` / reflect pipelines do not run | yes                         |
| `usage`       | the opinionated catalog a consuming project picks from                            | yes                         |
| `ai-hats-dev` | what the ai-hats repo wears to develop itself; no use to a consumer               | no (HATS-1834)              |

The layer is a property of the **component**, not of the bundle composing it: resolution is name-based across all roots, so a trait in one layer composing a skill in another is ordinary. The decision tree for a new component lives in `CONTRIBUTING.md`; the engine's own list is `LIBRARY_LAYERS` in `src/ai_hats/paths/constants.py`. Override precedence — see [9].

## Role

A root composition that the agent wears during a session — bundles traits, rules, skills, and an injection block into one config. The shipped library splits into three [layers](#library-layer): `library/core/roles/` (engine-internal: `initial-wizard`, `session-reviewer`, `judge-auditor`, `judge`, `role-judge`, `role-auditor`, `hypothesis-intake`, `test-agent`), `library/usage/roles/` (curated user-facing: `assistant`, `dev-python`, `dev-web`, `architect`, `sre`, `go-dev`, `go-dev-full`) and `library/ai-hats-dev/roles/` (this repo's own: `maintainer`, `role-curator`). Catalog — `ai-hats list roles`; layered structure and override precedence — see [9]. Example: [`ai_hats_library/usage/roles/assistant/config.yaml`](../packages/ai-hats-library/src/ai_hats_library/usage/roles/assistant/config.yaml). Customization (add / remove / override) — see [6].

Key system roles you will meet in cross-doc prose:

- `initial-wizard` — interactive setup that runs on `ai-hats self init`. See [6].
- `session-reviewer` — per-session retrospective; votes on active HYPs and files a PROP on self-problem. Triggered by `ai-hats reflect session` (auto on `session_end` per policy, or manual). See [5].
- `judge-auditor` / `judge` / `role-judge` / `role-auditor` — the reflection-loop roles. Backlog triage runs two-phase: `judge-auditor` (Phase 1, headless, read-only audit) → `judge` (Phase 2, HITL, ack'd mutations) via `ai-hats reflect hypothesis`. Role-coherence audits run via `role-judge` (`ai-hats reflect role`); `role-auditor` exists as a standalone L0 audit role for subagent delegation. See [5].

## Role spec

An expression evaluated at session launch time in `-r` / `--role` (e.g. `-r "maintainer + leader"` or `-r "maintainer - trait-base + trait-base-star"`). It starts with a base role name followed by ordered `+` (add) and `-` (remove) operations for traits, rules, or skills (HATS-1456). Runtime specs apply as an ephemeral third overlay layer and are never persisted to `ai-hats.yaml`. Quotes are required when spaces are present.

## Trait

An ai-hats-native composition primitive: a reusable bundle (rules + skills + injection text) included by one or more roles. Traits are the unit of cross-role reuse — a fix in one trait reaches every role that pulls it in on the next session. Flat model: a trait cannot include another trait. Format: `library/{core,usage,ai-hats-dev}/traits/<name>/config.yaml`. Catalog — `ai-hats list traits`. Composition rules — see [3]; library layout — see [9].

Key system traits every role inherits transitively:

- `trait-base` — minimum behaviour for every role: core principles (safety > integrity > convenience > velocity), pessimistic verification, brevity, least astonishment.
- `trait-agent` — agent-mode loop primitives: backlog state machine, delegation pattern, memory hygiene (context-reset / handoff / summary), anti-anchoring, tool-call hygiene.

## Rule, Skill

The two component kinds that ai-hats injects into the **provider** prompt, composed per session and delivered from the session cache (see [1]). They apply at the provider layer — the LLM reads them and follows; ai-hats does not interpret their content.

| Component | What it is                                                  | Format (under `library/{core,usage,ai-hats-dev}/…`)                     |
| --------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- |
| **Rule**  | Behavioural constraint (do / don't). No decision logic.     | `rules/<name>/rule.md`                                                  |
| **Skill** | Procedure, checklist, or protocol with steps and branching. | `skills/<name>/SKILL.md` (+ `metadata.yaml`, `scripts/`, `references/`) |

Catalog — `ai-hats list {rules,skills}`. Formats — see [3]; library layout and override precedence — see [9].

**Skill↔tool dependency.** A skill is portable `SKILL.md` content that **declares** the engine/CLI it drives via an optional `ai_hats.requires.{cli,mcp}` frontmatter block; ai-hats **verifies presence and warns** at compose/session time (with an install `hint`) and **never auto-installs**. Engine-owned skills bind to their engine by `requires`, **not** by living inside the engine package (which would invert the dependency arrow). `requires.mcp` is written once in a neutral form and compiled to each surface's native MCP channel (`.mcp.json` / `cline_mcp_settings.json` / `gemini-extension.json`). The `ai_hats.skills` entry-point remains the discovery seam for out-of-tree skill sources. Full rationale — see [ADR-0016](adr/0016-skill-tool-dependency-model.md) (amends [ADR-0014](adr/0014-composable-component-decomposition.md) §"Engine-owned skills").

**Rule-delivery contract (HATS-700 / HATS-1511 / HATS-1514 / HATS-1515 / HATS-1836).** Every composed rule's body is delivered into the prompt under the `## RULES` section. A rule is one file — `rule.md`; it carries no `metadata.yaml`, and a leftover one from an external library is never read (HATS-1836). Composed rules with empty bodies log explicit warnings. A `see rule X` pointer in prose or `composition.rules` in `config.yaml` across all library layers (`build_library_paths()`) must name a rule that exists in the library; the **rule-delivery-gate** pre-commit hook and the G2 unit test (`find_dangling_rule_pointers`) enforce this so an author never ships a pointer to a non-existent rule.

## Backlog

Three kinds of cards with strict state machines. **All operations go through the `rack` CLI** — direct access to `<ai_hats_dir>/tracker/**` is forbidden.

| Kind                 | ID         | Lifecycle                                                                                          |
| -------------------- | ---------- | -------------------------------------------------------------------------------------------------- |
| **Task**             | `HATS-NNN` | `brainstorm → plan → execute → document → review → done` (plus `blocked` / `failed` / `cancelled`) |
| **HYP** (hypothesis) | `HYP-NNN`  | `active → confirmed` / `refuted` / `stalled` — accumulates verdicts in `validation_log`            |
| **PROP** (proposal)  | `PROP-NNN` | `open → accepted` / `rejected` / `deferred` / `duplicate`                                          |

State-machine diagrams — see [4]. Day-to-day workflow — see [7].

**Plan home.** A Task's plan lives at exactly one canonical path —
`<ai_hats_dir>/tracker/backlog/tasks/<ID>/plan.md` — authored directly there via
Write/Edit after `rack transition <ID> plan`. `.claude/plans` is **not** a plan
home: ai-hats ignores it (the import path was removed in HATS-637), so any file
there is inert plan-mode scratch, not the plan. Discipline + draft→tracker
procedure — skill `plan-discipline`; readiness routing — skill `plan-gate`;
per-section enforcement — the engine gate (HATS-635).

- **Task ownership registry** — a single local, gitignored file recording which live session is *executing* each task, so a second agent can safely reclaim a task left mid-flight by a dead owner (`transition <id> execute` again — the `execute → execute` reclaim self-loop) and a live owner is never stolen (HATS-955). Reclaim-on-certain-death (owner pid + OS start-time, no TTL), single-slot per agent, ownership orthogonal to task state and anchored on `AI_HATS_ROOT_PID`. Full design — see [ADR-0015](adr/0015-task-ownership.md).

## Rack — `ai-hats-rack` / `rack` / `hatrack`

Three names for one thing, distinguished by layer. Use the one that names the
layer you mean:

| Name               | Layer                                                        | Where it lives                                     |
| ------------------ | ------------------------------------------------------------ | -------------------------------------------------- |
| **`ai-hats-rack`** | the Python **package** — the backlog kernel                  | `packages/ai-hats-rack/`                           |
| **`rack`**         | the **CLI** the package ships — the backlog surface you type | on `PATH` after install (`rack --help`)            |
| **`hatrack`**      | the **skill** that teaches a composed role to drive `rack`   | `core/skills/hatrack/`, composed via `trait-agent` |

The kernel is a light FSM plus transactional machinery (epic HATS-1014): FSM
topology declared in `backlog.yaml` (SSOT — [ADR-0017](adr/0017-backlog-yaml-single-definition.md)),
a transactional `transition` (FileLock → guard → in-memory mutation → two-phase
subscriber dispatch → single persist last), a structural lock model, and a
dispatch journal with actor identity. Everything beyond that — worktree,
ownership, scaffold, plan-gate, epic-automation, doc store, consumer hooks — is
an **extension** subscribing to kernel events, not kernel code.

`rack transition` is the single mutating verb: an ordered composite of ops
(`--state`, `--set`, `--log`, `--link`, `--attach`, `--freeze`, `--rm`) run in
argv order under one task lock with one persist, so any abort rolls the whole
sequence back. Day-to-day recipes — see [7]; engine reference —
[`packages/ai-hats-rack/README.md`](../packages/ai-hats-rack/README.md).

`rack doctor` is the read-only integrity report (HATS-1335): it scans every
backlog mounted in the project for dangling links, transitive link cycles,
mirror drift, duplicate list entries, missing required fields, and unreadable
cards. Exit 0 clean, exit 1 with findings; it never repairs — a "fixed" id is
a guess, so repair stays a human `transition --link/--unlink` decision. Since
HATS-1584 it also reports the **check bindings** (below): one line per point of
every carried row, classified against every mounted topology — `armed` (an edge
of the backlog the row names), `foreign` (an edge of a sibling's topology — the
legal cross-backlog skip), `dead` (an edge of nothing mounted), `unaddressed`
(a row under `apps.rack.<name>` no backlog answers to). The last two are
findings, so a gate that can never fire makes the report red; being the one
surface that mounts every backlog, the doctor is the only place `dead` and
`foreign` can be told apart. Findings and a typed failure share exit 1 — every
typed refusal in the package leaves through one `fail()` — so a caller branches
on the SHAPE under `--json`: a finished run reports `{clean, scanned, findings,
bindings}`, one that could not start reports `{error}`.

## Behavior experiment (A/B)

A scripted comparison proving that a library-component edit (skill / rule / trait wording) actually changes subagent behavior, instead of eyeballing it: `1 scenario × N arms × N identical runs`, scored mechanically (HATS-1053). Lives under `experiments/`. Term definitions (arm, scenario, score scripts, runs capture) and the authoring guide — see [10].

## Document (task document)

A file that belongs to a Task — `plan.md`, `summary.md`, a diagram, a sample
input. The store is **fs-as-truth**: the only way to write a document is to put
a file into `<ai_hats_dir>/tracker/backlog/tasks/<ID>/`. There is no `put` verb
and no manifest to keep in sync — `rack context <ID>` live-scans the directory
and digests on the fly, so a file written directly is visible immediately.

`rack context` reports each document as name + absolute path + mtime; `--json`
adds size and a `sha256:<12hex>` digest. Content is never inlined without an
explicit `--with <glob>` — the agent reads by the printed path.

**Frozen pins.** `rack transition <ID> --freeze <name>` pins `{name, digest}`
into `task.yaml::documents[]`, marking the file as evidence. The
frozen-integrity extension then aborts *any* transition whose pinned document
changed or vanished, naming both digests and the recovery recipe — no waivers,
including forced edges. Re-pinning drifted content or removing a pinned
document requires `--ack-frozen`. `--rm` trashes to `$TMPDIR` (recoverable),
never hard-deletes.

## Reflect

Retrospective and triage flows. The CLI subcommand `ai-hats reflect` is the single entry point.

| command                         | Spawned role                 | Mode                         | Purpose                                                                                                                                                                                                  |
| ------------------------------- | ---------------------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ai-hats reflect session`       | `session-reviewer`           | non-interactive              | Per-session retrospective: HYP verdicts + PROP-on-self-problem. Auto on `session_end` (policy `always` / `smart`) or on demand.                                                                          |
| `ai-hats reflect hypothesis`    | `judge-auditor` then `judge` | autopilot + HITL (two-phase) | Bulk triage: Phase 1 (`judge-auditor`, headless, read-only) produces a draft; Phase 2 (`judge`, HITL) discusses + ack'd mutations. `--headless` runs Phase 1 only (CI / cron-safe). HATS-513 / ADR-0007. |
| `ai-hats reflect all`           | `judge`                      | interactive (HITL)           | Deprecated — single-phase bulk triage with runtime mode-switch in the protocol skill. Kept for one bake cycle while `reflect hypothesis` rolls out; removal tracked as a follow-up task.                 |
| `ai-hats reflect role <target>` | `role-judge`                 | interactive review (HITL)    | Coherence audit of a single role against project context.                                                                                                                                                |
| `ai-hats reflect roles`         | `role-judge` *               | per-role HITL                | Bulk role audit — spawns one session per project role.                                                                                                                                                   |
| `ai-hats reflect issue`         | (no role)                    | non-interactive              | Log a supervisor observation as a new HYP, or merge into an active one.                                                                                                                                  |

**Reflection roles:**

- Backlog triage: `judge-auditor` (L0, read-only audit) → `judge` (L1, HITL + ack'd mutations). Entry: `ai-hats reflect hypothesis`.
- Role coherence: `role-judge` (L1, interactive review against project context). Entry: `ai-hats reflect role`. (`role-auditor` is a standalone L0 role available for subagent delegation).

L0 baselines (`base-auditor`) forbid CLI mutations and source-file edits; L1 baselines (`base-judge`) permit ack'd CLI from a whitelist. See [`ai_hats_library/core/traits/base-auditor/`](../packages/ai-hats-library/src/ai_hats_library/core/traits/base-auditor/) and [`base-judge/`](../packages/ai-hats-library/src/ai_hats_library/core/traits/base-judge/). `hypothesis-intake` exists for Haiku-class observation classification but is **not** wired into `reflect *` directly.

Practical recipes — see [5]. Pipeline architecture — see [8].

## Artifacts

What ai-hats persists on disk during normal use.

- **`ai-hats.yaml`** — project config. Fields: `schema_version`, `migration_step`, `provider`, `active_role`, `default_role`, `task_prefix`, `customizations`, `feedback`, `library_paths`, `venv_path`, `harness`. `harness` (HATS-764) pins the install-source channel — see **Harness source / channel**. `schema_version` describes the yaml format; `migration_step` (HATS-471) is a monotonic counter for one-shot migrations replayed at bump time — each entry runs once per project, then the gate short-circuits. Source of truth for composition, re-read at every session launch — edits apply on their own, with no command to re-run. `ai-hats self init` validates it and refreshes the project scaffold; verify the resulting composition with `ai-hats config status`. Full walkthrough — see [6].
- **`library_paths.yaml`** — user-global extra library paths config (`~/.ai-hats/library_paths.yaml`, HATS-1508). Fields: `paths: [<dir>, ...]`. Specifies user-level external library directories loaded during `build_library_paths` immediately after `~/.ai-hats/`, without modifying project `ai-hats.yaml` or using symlinks.
- **Harness source / channel** — the per-project choice of where `ai-hats self update` pulls ai-hats from, persisted as `harness.channel` in `ai-hats.yaml` (HATS-764). Three channels map to three audiences: **`local`** (ai-hats dev) — an editable install of a working tree (`uv pip install -e <path>`), a moving target reinstalled in place with no versioned dir; **`edge`** (own repos) — `git+https://<repo>@<branch-HEAD-sha>`, a moving target installed into `versions/<sha>/`; **`stable`** (end users, the **default**) — `ai-hats==<latest-tag>` from PyPI, pinned and semver-monotonic, installed into `versions/<tag>/`. A pure resolver maps `channel → (version_id, install_spec, mutable)`: **`version_id`** names the `versions/<version_id>/` dir (a `sha` for edge, a tag for stable; `None` for local's in-place install), and **`mutable`** selects the downgrade guard — the moving-target channels (edge/local) keep the git ahead/diverged guard, while `stable` runs a **semver-monotonic** guard (refuse a published tag whose version is lower than installed; override `--force-downgrade`). Set it with `ai-hats config set --channel {local|edge|stable}` (the wizard and config surface never hand-edit yaml); `AI_HATS_REPO_URL` overrides the edge repo. On a dev host whose ai-hats is an editable clone, `ai-hats self init` auto-seeds `channel: local` with `path` = the detected editable source (HATS-938) — no manual yaml edit — while a non-editable host keeps the `stable` default; override with `self init --channel {stable|local|edge} [--harness-path DIR]`. An absent `harness:` block loads as `stable` and saves byte-clean. See **Versioned install layout**.
- **SessionReview** — `<ai_hats_dir>/sessions/retros/sessions/<id>.md`. Output of `session-reviewer`: `summary`, `observations`, `hypothesis_verdicts`, `proposal_actions`. Schema `hats-session-review/v1`. Consumed by the next reflect cycle. Detail — see [5].
- **JudgeReport** — `<ai_hats_dir>/sessions/retros/judge/<UTC-ts>-report.md`. Output of `ai-hats reflect hypothesis` Phase 2 (or the legacy `ai-hats reflect all`) — HYP closures plus PROP decisions for one triage session. Detail — see [5].
- **JudgeDraft** — `<ai_hats_dir>/sessions/retros/judge/<UTC-ts>-draft.md`. Output of `ai-hats reflect hypothesis` Phase 1 (`judge-auditor`, headless). Carries proposed verdicts + a `## Proposed mutations` CLI checklist that Phase 2 executes after supervisor ack. With `--headless` this is the only artifact (no Phase 2). HATS-513 / ADR-0007.
- **RoleCoherenceReport** — `<ai_hats_dir>/sessions/retros/role-coherence/<UTC-ts>-<target>.md`. Output of `ai-hats reflect role` — findings on internal contradictions in a role composition. Detail — see [8].
- **Versioned install layout** — `<ai_hats_dir>/versions/<version_id>/` (a per-version venv, keyed by an edge `sha` *or* a stable tag — HATS-764) + a `versions/current` pointer-file (HATS-647). A managed `ai-hats self update` installs the new version into a fresh `versions/<sha>/` and atomically flips `current` (tmp-write + `os.replace`) only after a successful install + verify — so an update never mutates the venv a live run executes from, and an interrupted update never bricks the tool (`current` always points at a complete venv; on crash it stays on the old `sha`). The bash launcher resolves `current → versions/<sha>` once at run start and **exports `AI_HATS_VENV`**, pinning the whole run (hooks, sub-agents, bash-chained `ai-hats … | ai-hats …`) to one `sha` even if `current` flips mid-run (pin-at-spawn). Applies only to the managed default venv; editable / dev installs and explicit `AI_HATS_VENV` / yaml `venv_path` overrides bypass versioning, and a pre-versioning `.venv` is the lazy fallback. Completeness is gated by a **`.complete` sentinel** written last — only after a fully-successful install + verify — so it is robust to a build killed mid-pip, independent of pip's internal file-write ordering (HATS-648; HATS-790 removed the legacy `bin/ai-hats` console-script proxy this note used to contrast against — the launcher now execs `bin/python -m ai_hats`); `read_current_sha` resolves a `sha` only when its venv carries the sentinel and a runnable `bin/python`. Incomplete residue (a `versions/<sha>/` lacking `.complete`, e.g. a crashed install) is reclaimed idempotently by the **`version_recovery`** sweep — TTL-guarded, run at both the `create_session` chokepoint and `self update` start, never touching `current` or a complete dir (HATS-648 / R1). Complete-but-superseded versions are reclaimed by the **liveness-ref GC** (HATS-649 / R2, next entry).
- **Liveness ref / orphan-version reclaim** — `<ai_hats_dir>/versions/.refs/<root_pid>.json` carrying `{run_id, root_pid, start_time_utc, sha}` (HATS-649 / R2). Every run writes/refreshes its ref at the `create_session` chokepoint, recording the managed `sha` it executes from (`sys.prefix` under `versions/`; legacy `.venv` / editable installs write none). `reclaim_orphan_versions` then removes any **complete, non-`current`** version that no **live** ref pins — **reclaim-on-certain-death**: a ref is live iff its `root_pid` is alive *and* the recorded `start_time_utc` (via `ps -o lstart=` under a pinned `TZ=UTC`/`LC_ALL=C`, with an `os.kill` fallback) still matches, so a reused pid is detected as dead. The pin is load-bearing: `lstart` renders in the TZ and locale of the `ps` process, so unpinned an ambient difference between the writing run and the checking pass read as reuse — reclaiming the venv a live run executes from (HATS-1339). A legacy `start_time` is ignored rather than compared, so such a ref keeps its version while its pid lives. Single-host, **no TTL** for this pass; dead refs are swept in the same pass so refs never leak. Conservative — a live ref, `current`, a `self update`'s `target_sha` (`keep_shas`), an incomplete dir, or the `.refs` store itself is never touched; the legacy `.venv` lives outside `versions/` and is reclaimed only by HATS-653. Recovery is an injected `EnvironmentRecovery` collaborator on `SessionManager`, so both the HITL (`WrapRunner`) and Automate (`SubAgentRunner`) paths converge through it — closing the gap where the sweeps ran only on the WrapRunner path. The reclaim and the `self update` install both run under the **version GC/acquire lock** (HATS-650 / R3) so a concurrent run can never reclaim a version mid-flip.
- **Legacy `.venv` reclaim** — `reclaim_legacy_venv` removes the orphaned pre-versioning `<ai_hats_dir>/.venv` once the versioned install is authoritative (HATS-653 / Phase B). After lazy migration the legacy `.venv` only ever resolves as a *fallback* (launcher / `venv_path` precedence consult it solely when `versions/current` is absent or broken); never updated again, its fallback value only decays. The single guard is **`current_run_sha(project_dir) is not None`** — running from a complete `versions/<sha>/` venv proves in one predicate that (a) we are *not* on `.venv` (so discarding it can't pull the rug from the live interpreter), (b) no `AI_HATS_VENV` / yaml `venv_path` override and no editable / dev checkout is active (each resolves `current_run_sha → None`, so a user-owned venv is never touched), and (c) a healthy versioned venv exists. Removal is via `safe_delete.discard` (idempotent), the reclaimed path returned for no-silent-caps logging by the caller, run at the same two convergence points as the R2 reclaim — the `create_session` chokepoint (`EnvironmentRecovery`) and `self update` start. The **first** migration `self update` runs *from* `.venv` (`current_run_sha → None`) and correctly skips; the reclaim converges on a later versioned invocation. Reclaim is **reversible**: if a versioned install later breaks and `.venv` is gone, an arbitrary command fails loud with "Run: ai-hats self update", whose launcher `heal_if_needed` recreates `.venv` and rebuilds versioned — so B deliberately drops the *silent stale-fallback* (superseding the HATS-649 "preserve `.venv`" note) in exchange for bounded disk and never running ever-staler fallback code.
- **Version GC/acquire lock** — `<ai_hats_dir>/versions/.gc.lock`, a crash-safe `fcntl` advisory lock (via `filelock` — the same library + pattern as the worktree locks, a ~15-line wrapper, not a hand-rolled lock) serializing the two mutating sections of the versioned layout (HATS-650 / R3): the **acquire** section of `self update` (the `version_recovery` sweeps + install/reuse + the `current` flip) and the **GC** section at the `create_session` chokepoint (`sweep_incomplete_versions` + `reclaim_orphan_versions`). It closes the corruption window where an installer has written `.complete` but not yet flipped `current`: in that window the target is a complete, non-`current`, unreferenced dir, so a *concurrent* GC in another process would reclaim it and the flip would land on a deleted dir (bricking the tool) — `keep_shas` only protects the installer's own process. The acquire site **blocks** with a generous timeout (a second concurrent `self update` waits, then a clean "another update in progress" exit on `VersionLockError`); the hot GC site is **opportunistic** — a short timeout, swallowed, so a held lock skips the GC rather than ever blocking or breaking session start (the next invocation converges). Because it is an `fcntl` lock the kernel releases it on process death, so a `kill -9` while held never wedges future cleanup — never a create-lockfile/delete-on-exit scheme. Single-host (`fcntl` is unreliable on NFS/SMB).
- **Launcher contract & skew advisory** — the host launcher is a **copy** installed once by `install-launcher.sh` and it never self-updates, so it drifts behind the package silently (HATS-1617; HATS-1600 spent a session diagnosing a two-week drift). The drift is made visible by a monotonic **`LAUNCHER_CONTRACT=<int>`** literal carried inside `scripts/ai-hats-launcher` itself — bumped only when the launcher's *resolution behaviour* changes (venv/project resolution, pin scope, dispatch), never for comments or a release, and never a content hash (which would cry skew at a reworded comment). The stamp has to travel inside the file because the public install is `curl … install-launcher.sh | bash`, which has no package-version context. The package holds the matching `constants.LAUNCHER_CONTRACT`, and a drift lock (`tests/test_launcher_contract.py`) keeps the two equal. Skew is **behind-only**: one host launcher serves N projects, so being newer than an old project is correct, not skew. Two contours read it, because neither can see the other's failures: (1) **failure path, bash** — when the launcher cannot resolve a venv it dies *before any interpreter runs*, so nothing in Python can report there; it compares its own literal against `<ai_hats_dir>/launcher-contract` (a one-line marker `write_canonical` leaves on disk, untracked by `MANAGED` like `versions/` beside it) and, on skew, replaces the `self update` / `self init` hint — advice a stale launcher cannot act on — with the refresh command. Silent on success, and silent when the marker is absent or unparseable. (2) **success path, Python** — `self update` compares the *installed* launcher file's stamp (via `_installed_launcher_path`) against the package constant, catching a launcher that runs fine but resolves by superseded rules. Contour 2 replaced the HATS-655 *dormant versioned-layout advisory*, which read one symptom of the drift (a `versions/<sha>/` install ignored in favour of the legacy `.venv`) and was mute on every other; it is also the **only** contour that catches launchers already stale before HATS-1617, since a copy can only carry a check that existed when it was made. **Non-mutation invariant:** both contours only print — they NEVER write the host launcher. It is host-global (one entry point for ALL projects) and the least-recoverable component (a broken venv self-heals; a broken launcher cannot — it *is* what runs `ai-hats`), so a per-project write would risk cross-project breakage and a bootstrap-brick; refreshing stays a deliberate host-level act.
- **Install layers (DATA / MANAGED / RUNTIME)** — the recovery classes a partially-destroyed `.agent/` sorts into, and the taxonomy `ai-hats self update --check` reports (HATS-595). **DATA** (`tracker/`, `user-rules/`) is hand-authored: nothing regenerates it, so the only remediation is a snapshot tarball — `--check` names the newest one under `/tmp/ai-hats/bump-backups/` (the pre-bump snapshots `migration_backup.py` writes; override the dir with `AI_HATS_BUMP_BACKUP_DIR`) with a ready `tar -xzf` line, and never heals it automatically. **MANAGED** (`library/`, and every hook command path in `.claude/settings.json` resolving) is scaffold `ai-hats self init` creates and maintains — equivalently any `self update`, whose bump runs the same `Assembler._refresh`, which is why there is no separate heal step. Note the direction: `<ai_hats_dir>/library/` is where **project-local, user-authored** components live, not an export of the installed library — framework rules and skills are never copied there. **RUNTIME** (the managed venv and its drift vs upstream) is disposable and rebuilt by `ai-hats self update`; drift is read from the TTL-cached update-check probe, so `--check` stays offline and reports `unknown` rather than failing when no probe has run. Only a broken layer is blocking: `--check` exits **1** on any BROKEN row and **0** when healthy or warn-only (a venv N commits behind is a warning), keeping `2` for usage errors. It is diagnose-only — it writes nothing and refuses to combine with the mutating flags.

## Session materialization & dry-run

- **Materialization port** — the single seam every session write goes through (`ai_hats/materialization.py`, HATS-1211). One interface, two implementations: **`ApplyMaterializer`** performs the write and records it, **`PlanMaterializer`** records the same entry and touches nothing. Shapes: `write_text`, `copy_tree`, `mkdir`, `merge_json` (read-modify-write of a user-owned file), `remove_tree` (materialization is not append-only — a rebuild deletes first), plus `lock` (taking a `filelock` creates a file, so a dry-run must not take one). Both implementations build their entries from the same `describe_*` functions, so the record cannot differ by implementation — a contract test suite runs against both. The port rides `BuiltArtifacts.port` and is an explicit constructor argument everywhere: no function initialises its own.
- **Materialization plan** — the ordered record a port accumulates (`MaterializationPlan`): per entry the kind, target, byte size, file count, and for `merge_json` the key-level diff. `duplicates()` names targets materialized more than once — one file produced twice, which is a defect rather than a rebuild (remove-then-create on one path is not counted).
- **Session dry-run** — `ai-hats -r <role> --dry-run` (HITL) and `ai-hats agent <role> --task … --dry-run` (Automate): run the real assembly with a `PlanMaterializer` and report what a launch *would* deliver — resolved role → provider, run mode, effective policy, the launch argv (or SDK options), env **key names only** (values carry secrets), the composed prompt path (`--dry-run-full` dumps the body), and the materialization plan. `--dry-run-json` emits the same payload machine-readably; the human view is a rendering of that dict, never a second assembly. It creates no session record, no worktree, no ownership hold and no audit entry, and composition is taken non-interactively so the first-run `active_role` write does not fire.
- **The dry-run guarantee** — a dry-run leaves the filesystem **byte-identical**. This is what makes escaping the port impossible to do quietly: a write that goes around it happens for real during a dry-run and is caught. Reported as **escapes** — paths that appeared during a plan-mode build; the dry-run removes them again and names them, so a bypass is loud rather than silent. **Notes** carry the complementary case: a gap between what the report can observe and what the surface actually delivers (today, claude/Automate recomputing its prompt outside the builder) is stated rather than left implied.
- **Sub-agent first turn** — the per-task context a spawned agent is handed, as distinct from its per-role composition: `# TICKET_CONTEXT` (the subject card's raw `task.yaml`), `# LINKED_CONTEXT`, `# TASK`, in that order, empty sections skipped. Claude assembles it as the SDK's first user message (`sdk_options.assemble_first_user_message`); the CLI surfaces mirror the same three sections in one argv token via `session_artifacts.assemble_meta_prompt`, which additionally inlines the role text (no `system_prompt` channel to put it in) and a `# WORKING_DIRECTORY` block so `rack` resolves the right backlog (HATS-1479). Both are reached through `Surface.describe_automate_launch`, so the prompt saved to `<session_dir>/meta_prompt.txt` and shown by `--dry-run` is the one that ran — a report assembled by a second function is a report about a different launch (HATS-1552). A fourth section, `# PROJECT_STATE` (the whole-backlog `STATE.md` dump), was dropped in HATS-681 — ~5.4K tokens of mostly-finished cards per spawn, which the backlog CLI serves on demand instead; its parameter outlived it until HATS-1100, and regression tests now pin the absence of both. See [13].
- **`linked_context`** — the assembly behind `# LINKED_CONTEXT` (`src/ai_hats/linked_context.py`, HATS-689): the cards a ticket links to **directly**, one level, no transitive walk. Pulled in salience order `parent_task → depends_on → related → see_also`, deduped, self and unresolvable targets skipped. Per card a trimmed view — id, title, state, description — plus **only the latest** `work_log` entry, the same token-hygiene argument that dropped `PROJECT_STATE`; the parent epic additionally carries its whole `plan.md`. That last one is the only **unbounded** input on this path — there is no truncation anywhere in the module, so a long epic plan reaches the prompt in full. Failure is deliberately asymmetric: a corrupt *neighbour* is skipped in silence, while a corrupt *subject* card logs at ERROR, because folding it into `""` would hand the agent a prompt with no epic and no links, indistinguishable from a card that has none (HATS-1373).
- **Session wiring vs project installation** — the boundary between per-session hook delivery and long-lived project setup (HATS-1207 R3 / ADR-0018 §2.1). **Session wiring** is the per-session hook activation emitted by the builder (`<cache>/settings.json` + `--settings` for Claude, `<cache>/hooks.json` + global dispatcher for Agy) and is gated by `SessionPolicy(hooks=False)`. **Project installation** is long-lived setup (installing git hooks in `.githooks/`). Runtime hooks live in the session tree (HATS-1268, HATS-1480); worktree hooks spawn in place from their declaring skill (HATS-1269). Shared across sessions and human runs; a `SessionPolicy` gates session wiring ONLY and must never uninstall shared project installation state.
- **Storage root** — a top-level directory with a single owning writer and a single lifetime ([ADR-0021](adr/0021-surface-materialization.md) S3). There are five: the installed package, `<ai_hats_dir>`, the project root, `$HOME`, and the session tree. Every materialized file belongs to exactly one root and inherits its write and cleanup rules.
- **Write point** — a place in code from which a storage root is allowed to change (ADR-0021 S3). Four today: install-time `_refresh` (init/update), `set_role`, session build, spawn — with `set_role` ruled a relic and being retired (HATS-1474), leaving three. A write that reaches a root around its write point is a defect.
- **Skills mirror** — the per-session copy of every composed skill's directory, placed where the surface CLI scans for skills (`plugin/skills/` for claude, `rules/.agents/skills/` for agy, `skills/` for cline); wiped and rebuilt whole on every build, with `SKILL.md` re-rendered from the source — the copy is never read back (ADR-0021 S4).
- **Hook wiring** — the per-session file binding surface events to hook commands (`settings.json` for claude, `hooks.json` for agy). The same artifact **Session wiring vs project installation** above calls *session wiring*; the registration vs runtime-invocation split — ADR-0021 S5.

## Lifecycle checks

- **Check binding (`composition.apps`)** — a row on a trait's or role's `composition:` that attaches a script to a lifecycle point of one application: `apps.<app>[.<level>…] -> [{run: <skill>/<script>, at: [<point>], on_error: refuse|warn, …}]` (ADR-0019 D2, reshaped by HATS-1545). ai-hats owns **three** keys of a row — **`run:`** (what executes), **`at:`** (where) and **`on_error:`** (how a verdict is read) — and carries every other key verbatim as *cargo* to whoever owns `<app>`. `at:` is owned but never *interpreted*: ai-hats guarantees only that a row names at least one point, because a row bound to nothing is a gate that never fires; what each name MEANS is the application's question. The depth between the app key and the row is likewise the app's own grammar and ai-hats never checks it. Two apps exist today: **`rack`**, which puts the backlog it gates one level down (`apps.rack.tasks`, addressable by the backlog's `name` or its `cli_alias`; grammar in ADR-0017 §3, restated for consumers of the package in `packages/ai-hats-rack/README.md`) and reads `at: [<from>-><to>]` — or `at: [-><to>]` for every road into a state (ADR-0017 §3); and **`wt`**, ai-hats's own, whose rows sit directly under the key and whose `at:` names a point of `check_points.wt_points()`. The **skill ships the capability, the composition decides the policy** — so the same script binds to different points, with different failure policy, per trait/role/project, without forking the skill. `SKILL.md` carries no part of it. A row names a skill it does not pull in: binding to an uncomposed skill is an error, not an implicit compose. Distinct from the three *hook channels* (`git_hooks`, `runtime_hooks`, `worktree`), which are declared in `SKILL.md` frontmatter and bake their own attachment point. A fourth, `lifecycle_hooks`, was retired in HATS-1147 (ADR-0019 D8); declaring it now fails composition. *The flat `checks:` list this replaced is retired: a config still carrying it gets a typed refusal naming where the rows moved — dropping it with a warning would lose a declared gate, which is the silence this channel exists to remove. `at:` replaced `on:` because YAML 1.1 reads a bare `on` as `True`.*
- **Extension point** — a named place a row may attach to. Since HATS-1545 there is no single catalog: the **application owns its point names**, and ai-hats validates only its own. `rack` (ADR-0017 §3): `<from>-><to>` for one FSM transition and `-><to>` for every road into a state — a subscriber runs every row bound to the edge being taken, in-lock at priority 15 (HATS-1141); `card:pre-create` is rack's too and still has no caller. `wt` (ai-hats's own, `check_points.wt_points()`): `pre-merge`, and nothing else — it fires in `merge()` after the cheap local guards and before every mutation, on both `ai-hats wt merge` and the FSM automerge (HATS-1540). `create` and `teardown[merge|discard|cleanup]` sat in this catalog until HATS-1577 with no call site, so a binding to one composed clean and never ran; they come back together with that call site in HATS-1146, as `pre-reclaim` does in HATS-1145 (*planned*). A point of the `wt` app that ai-hats does not fire is a composition-time refusal; a point in another app's cargo is that app's question, and it decides — the rack skips a point naming an edge its topology lacks rather than refusing, since a typo and a point aimed at a sibling topology are the same fact from the carrier's side. A *subscriber* holds one topology and so cannot tell them apart either; `rack doctor` holds every mounted one and does — it reports the first as `dead` (a finding) and the second as `foreign` (HATS-1584). Refusing the transition on a dead point is HATS-1578 and is not in yet. A check signals **refuse** with **exit 2** — never exit 1, which is what a shell script produces by accident under `set -e`; any other non-zero status means the check itself broke and is governed by `on_error`.
- **Consent point (`consent:` under `apps.consent_gate.<operation>`)** — a selector at which a role requires the external session wrapper to obtain human authorization before starting a top-level command. The operation adapter owns selector grammar and argv matching; the wrapped tool and executable check rows do not read the declaration. Consent is three-valued during composition: absent says nothing, `true` arms, and `false` disarms the same `(operation, selector)` declared earlier. The resolved policy is frozen at session launch. A `consent:` key under any other app is refused, because silently accepting the retired `apps.rack` / `apps.wt` form would leave the command unprotected (ADR-0030).
- **Consent ticket (`AI_HATS_CONSENT_TICKET`)** — the one-shot nonce the guard mints when it raises a consent question, written under `<git-common-dir>/ai-hats/consent/` and injected into the approved command by rewriting it. Bound on four axes — the card, the session, the exact argv, and the single unlink that spends it — and on **no clock**: the ticket is written when the question is RAISED, so any expiry would be the supervisor's budget for thinking (HATS-1682). The remaining age is housekeeping only (`STALE_AFTER_SECONDS`, 12h), and the engine is what sweeps it, because the agent cannot tidy the store itself — `rm` under it is refused, and must be, or a gate could clear the evidence it is judged by. Three sweepers, none of them the agent: `mint` and `consume` prune as they go, and `WrapRunner` calls `consent_ticket.sweep` once at the start of an **interactive** session. `SubAgentRunner` — the batch sub-agent — does not, so a headless run's leftovers wait for the next mint or the next interactive session. A redirect is stripped from the binding (the shell eats it, `rack` never sees it); a second command chained after the gated one is not, because it is not what the supervisor was shown. Typing a ticket inline is refused as a self-grant.
- **Consent grant** — one supervisor answer covering a SERIES of operations for a named window, written to `<session_cache_dir>/consent/grants/<id>.json` (mode `0600`, dir `0700`). Where the **consent ticket** is bound to one exact `argv`, the grant is bound on three axes only — the session, the project, and a deadline — because it is issued BEFORE the command exists, so there is nothing to key it on. Radius is `types` alone, `fnmatch`; there is no subject axis (ADR-0029 D5b — binding a grant to one card would mean reading its id out of a command line the guard sees BEFORE the shell expands it, and a loop over `$id` hands it the literal token). Grants are **additive** (D5a): issuing writes a new file and touches no live one, so the radius can only ever widen — `consent rack.transition 1` over a live 30-minute window does not shorten it; the budget axis (`N operations`) is deliberately absent — "one consent for several moves" is expressed in time, never in a count (ADR-0029 D5). The default window is **120 minutes**, a constant at the top of `hooks/consent_gate/issue.py` so a supervisor can edit it without reading code. Revocation is restarting the session: a new session gets a new cache dir, so the old grant is unreachable by path isolation rather than by deletion — which is also why the `expires_at` check stays load-bearing, a cache dir outliving a SIGKILLed owner by days having been measured. **Nothing in ai-hats ever mints one**: a grant written at the moment of a question would survive a "No" and open the next call, so the only writer is the person typing the verb (ADR-0029 D10).
- **Consent wrapper** — session-local command middleware composed from the launch-frozen role policy. It recognizes a protected operation through an external adapter, verifies the available human authorization before spawning the original executable, records a successful use, and then delegates the complete top-level command. The wrapped CLI contains no consent policy or authorization channels; nested effects are covered by the one wrapper decision. A new tool joins this system through an `apps.consent_gate` declaration plus an external adapter, not by importing the consent engine [12].
- **`consent` (the verb)** — the command a PERSON types to issue a grant, unprefixed on purpose: the short name IS consent leaving ai-hats, and the place it is typed — a chat shell escape — has neither completion nor hints (ADR-0029 D3). Positional grammar, trailing number is minutes: `consent`, `consent all 30`, `consent rack.transition 30`. The word is either `all` or ONE declared operation type; anything else is refused. A type the role did not declare under `apps.consent_gate` is refused rather than written, so a typo cannot become a grant that opens nothing. It prints the radius and the deadline and never the key — its stdout lands in the model's context on every surface that has the escape. Run by the AGENT it is not a hole but the request channel: PreToolUse fires on the agent's commands and not on a person's `!`, so the attempt becomes the question it was going to have to ask (ADR-0029 D12). Shipped as a console script of `ai-hats-library`, and named in the allow-rule lint for the same reason `rack transition` is: under `permissions.allow` the agent would write itself a grant in silence, and a grant is wider than a ticket.
- **`apps.consent_gate`** — the declaration block naming which operation types and selectors a role wraps (`rack.transition`, `wt.merge`, `wt.discard`). It is the assimilation contract between role composition and the external **consent wrapper**: the declaration selects policy, an adapter recognizes the tool's command grammar, and neither the generic serializer nor the wrapped tool learns consent semantics. The launch-frozen declaration is read by the verb, runtime guard and wrapper integration layer [12].
- **Session skill mirror** — the per-session copy of every composed skill each surface writes at session entry, whole-directory (so sibling data files survive), each at its own path: `<cache_root>/sessions/<sid>/plugin/skills/<skill>/` (claude), `<sid>/rules/.agents/skills/<skill>/` (agy), `<sid>/skills/<skill>/` (cline) — see [1] for `<cache_root>`, which is outside the project. It is what the agent's own skills, the runtime hooks and a **bound check** all execute from inside a session (ADR-0019 D9). Because the paths differ per surface, the root is *asked of the provider* (`Surface.session_skills_root`) rather than guessed — resolving into any one of them by name would make a gate silently vanish on the other two. Outside a session there is no mirror and a check resolves from the live library by composing the active role. *Until HATS-1540 the check channel kept a private fourth copy at `<sid>/checks/<skill>/` ("session check snapshot"); it held only the **bound** skills, so a session started before a binding existed had no root and refused every transition until restart.*
- **Card gates — `->merge` and `->done`** (HATS-1137 / HATS-1614, ADR-0023 D3/D4). The two gates a card passes on its way into master, named after the **edge** each guards and not after the point it hangs on. **`->merge`** (`hooks/merge-gate.sh` at `wt:pre-merge`) asks *is this branch fit to enter master*; the agent is alone at that refusal, and it costs nothing because nothing has merged yet. **`->done`** (`hooks/done-gate.sh` at `->done` — EVERY road into the state, not just the review one, since HATS-1719: the teardown-merge fires on 8 of the 8 edges into `done` and this gate covered 1, so a forced close merged with the question never asked) asks *is master green after this card* — the one question no earlier gate can ask, since two independently green branches can make a red master; the supervisor is present here, so a refusal needing coordination between agents belongs to it. What each runs is the **project's** answer, never the library's: both ask `scripts/ci-local.sh --stages <gate>` and refuse an empty one (ADR-0023 D7). `->merge`'s composition is kept a **subset** of `->done`'s so one run pays for both — see **Gate marker**. Both are *marker lookups* on the critical path; the suite runs out of band via `make merge-gate` / `make done-gate` in the task worktree. A third gate, **push** (`git_hooks/pre-push-e2e-master.sh`, marker name `e2e-gate`), guards `git push` to master with the full e2e tier and is not a card gate.
- **Gate marker** — the file a green gate run leaves at `<git-common-dir>/ai-hats/<gate>/<tree>`, carrying `tree=`, `timestamp=` and `stages=` (the composition it actually ran). **Keyed by tree, not by commit**: the automerge is `--no-ff`, so a merge commit's sha is always new while its tree is usually byte-identical to the branch's — keyed by commit, a card paid twice for one content. **`--git-common-dir`, never `--git-dir`**, which is what makes a marker written *inside* a task worktree visible *from* the main checkout. It cannot go stale in either direction: different content is a different key, and a gate that grew a stage stops honouring markers that never ran it (required ⊆ recorded). **Written per gate, read across gates** (HATS-1614): a lookup unions what *every* gate recorded for that tree, so a fuller run stamps the gates its composition contains — the **absorption rule** (ADR-0023 D5). Only written on a **clean** tree: on a dirty one the run still counts as a run, but what passed is not what the branch holds.
- **`in_process` vs `detached`** — which of the two a hook channel is, decided by *who is running when the script spawns* (ADR-0019 D10), not by whether bytes are copied per session — the two axes are orthogonal, and `checks` is the case that shows it: `in_process` **and** resolved against a per-session copy. **`in_process`**: ai-hats itself spawns it, so an absolute path suffices — no manifest, no registration, sibling files intact. Worktree hooks resolve that path fresh at spawn; `checks` and claude's runtime hooks resolve it against the session skill mirror instead, for byte-stability against a library edited mid-session, which is a property of those channels and not of the mode. **`detached`**: a third party spawns it with no ai-hats process alive, which forces materialization to a stable self-describing directory plus a manifest and a fail-closed backstop. Covers `git_hooks` alone — a human `git commit` has no process able to resolve the library root, and git requires a real executable named exactly `<event>` under `core.hooksPath`.

## Host tool & self-location

How ai-hats is invoked and which code actually runs. The throughline: ai-hats is a **host tool driven by the launcher / `python -m ai_hats`**, never a project app-venv dependency. Full rationale: [ADR-0010](adr/0010-bootstrap-paradox-self-location-and-forward-safe-config.md).

- **Managed venv / managed-venv invariant** — ai-hats is a **host tool**, not a project dependency. It is invoked by the host-global bash launcher at `~/.local/bin/ai-hats` (`AI_HATS_LAUNCHER_DEST`), which resolves a per-project **managed venv** and exec's `<venv>/bin/python -m ai_hats "$@"`. The invariant: ai-hats lives in a venv ai-hats *manages* — the default `<ai_hats_dir>/.venv` (or a `versions/<sha>/` blue-green dir, see **Versioned install layout**), an explicit `AI_HATS_VENV` pin, a yaml `venv_path:` override, or an editable dev checkout — and is driven via `python -m ai_hats`. It is **never** a dependency of a project's own application venv. HATS-790 (Alt 5) removed the `[project.scripts] ai-hats` console-script generator, so **no venv materialises a `<venv>/bin/ai-hats` proxy**; the only `bin/ai-hats` worth invoking is the HOST launcher. Venv health is probed by `bin/python` + `python -c "import ai_hats"` (importability), not by the removed binary. The classifier of sanctioned vs not is the pure `classify_invocation` (see **self-location guard**).
- **Self-location guard** — a runtime backstop (`ai_hats.self_location.classify_invocation`, wired by `_guard_self_location` into `main_entry`) that **refuses-and-instructs** when ai-hats is running from a FOREIGN (non-managed) venv — the residual **stray shadow** case after HATS-790 closed the console-script vector (HATS-791, Alt 3). The decision is a **pure** function returning `"sanctioned"` or `"foreign"`; on `"foreign"` it prints `remediation_text` to stderr and `sys.exit(3)`. It biases **HARD toward fail-open**: `"foreign"` is returned only when positively certain the running interpreter (`sys.prefix`) is a real venv that is none of the sanctioned shapes — every ambiguity (no project, unresolved venv, any path error, an editable host clone, an under-`.agent/ai-hats/` managed prefix) resolves to `"sanctioned"`. **Scoped to an existing managed venv:** the guard only refuses when the venv ai-hats *would* resolve for this project actually exists on disk (nothing to shadow ⇒ nothing to protect). **Info commands are exempt** — `--version`, `--help`/`-h`, `--tree`, and a bare `ai-hats` resolve no project state, so `_is_guard_exempt_invocation` skips them. Wired into `main_entry` (the real-invocation path) but **NOT** the `main` click group, so in-process `CliRunner` tests bypass it. **Operator escape hatch:** `AI_HATS_SKIP_SELF_LOCATION_GUARD=1` (`SKIP_ENV_VAR`) always returns `"sanctioned"`. It is a person's hatch, so the launcher **withholds it from a sub-agent** — and because the verb sits at the front of the name rather than in the suffix, `withheld_from_subagent` cannot recognise it by shape and names it explicitly (HATS-1872). It is defense-in-depth, not a primary gate: a missed shadow merely reproduces pre-guard behaviour while a false positive would brick a good CLI.
- **Stray shadow** — a stale `ai-hats` reachable on `$PATH` ahead of the host launcher, typically a project app-venv into which a user once `pip install`ed ai-hats. Before HATS-790 such a venv carried a generated `bin/ai-hats` console script that `direnv` (or any rc prepending a venv `bin/`) would reach first, silently running stale code mis-resolved against the wrong project. A shadow is **only ever a PATH-resolution outcome** (absolute-path invocations are immune — see **out-of-band recovery**). HATS-790 removed the generator that created the common shadow; the **self-location guard** is the runtime backstop, and a **stray-shadow detector** WARNs about any remaining one: `ai_hats.cli.maintenance.find_stray_launchers` (python) and its bash twin `detect_stray_launchers` in `bootstrap.sh` scan `$PATH` for `ai-hats` executables whose resolved path differs from the sanctioned launcher. Both **NEVER delete** (destructive-actions rule) — they instruct the user to uninstall ai-hats from the shadow's venv or remove the file and front the host launcher on PATH.
- **Out-of-band recovery** — the recovery path for when in-band `ai-hats self update` **cannot heal itself** (a managed venv broken badly enough — deleted site-packages, dangling interpreter, a foreign shadow — to be unrunnable, the *bootstrap paradox*: the tool that must do the fix is the broken thing). `scripts/bootstrap.sh` is the canonical hatch (HATS-791) and is **paradox-immune** by two properties: it is always **fetched fresh** (`curl -LsSf …/bootstrap.sh | bash`) and it drives the launcher by **ABSOLUTE path** (`"$LAUNCHER_DEST"`), never the on-`$PATH` `ai-hats` — so a stray shadow cannot intercept it (an absolute path does not consult PATH: **absolute-path immunity**). The dedicated recovery entrypoint is the **`--repair`** flag: it force-reinstalls the launcher, removes only the framework-managed default venv (`.agent/ai-hats/.venv` + `versions/`, never a user-owned `AI_HATS_VENV` override), then re-runs `"$LAUNCHER_DEST" self update` to rebuild from scratch. Idempotent; also runs the stray-shadow detector. Usage: `curl -LsSf https://github.com/muratovv/ai-hats/raw/master/scripts/bootstrap.sh | bash -s -- --repair`.
- **Config forward-compat policy** — how an OLDER ai-hats handles an `ai-hats.yaml` a NEWER ai-hats wrote, keyed off `KNOWN_SCHEMA_VERSION` (`ai_hats.models`, currently 4 — the highest `schema_version` this binary understands). Two complementary rules (HATS-792): **(1) same-version unknown fields are preserved, not dropped** — `ProjectConfig.from_yaml` pre-strips unknown top-level keys before `extra="forbid"` validation (so the older binary survives a field a newer one added without a schema bump, e.g. `migration_step`), but stashes the popped `{key: value}` on a `_extra` `PrivateAttr` that `to_dict` merges back, so read→write **round-trips** the field instead of silently deleting it on the next `save()` (mirrors the `TaskCard.extras` capture-on-load / merge-on-dump pattern); the HATS-581 stderr WARN still fires so the vanish-from-the-typed-model stays observable. **(2) a genuinely newer schema fails loud** — when on-disk `schema_version` exceeds `KNOWN_SCHEMA_VERSION`, `from_yaml` raises `ProjectConfigError` pointing at `ai-hats self update` rather than misreading the file as v4 and risking a clobber, and a matching **`save()` clobber guard** refuses to overwrite a file whose on-disk `schema_version` is newer than this binary knows (defending bypass paths that build a config without first loading the existing file). Preserve covers *same-version* skew; fail-loud covers *newer-schema* skew; the two never overlap.

## Session identity & the env contract

How a running [Session](#session) says who it is to every process it spawns, and how a process decides whether to believe an identity it inherited. Full rationale: [ADR-0025](adr/0025-session-identity-env-contract.md). Russian names are given because the ADR and the code comments use them.

- **Session pin (пин сессии)** — the identity a live session exports into its children's environment: ten keys (`AI_HATS_SESSION_ID`, `AI_HATS_PROJECT_DIR`, `AI_HATS_DIR`, `AI_HATS_VENV`, `AI_HATS_SESSION_CACHE_DIR`, `AI_HATS_ROLE`, `AI_HATS_ROOT_PID`, `AI_HATS_SESSION_IDENTITY`, `AI_HATS_PYTHON`, `TRACE_LOG_PATH` — ADR-0025 D1), of which `AI_HATS_PROJECT_DIR` is the authoritative statement of **which project the session belongs to**, and `AI_HATS_DIR` / `AI_HATS_VENV` are scoped by it. Children inherit it whether or not they stay in that project — an `ai-hats`, hook or gate running in a *different* project sees a **foreign pin**, which means "belongs to another session", not "differs from cwd". Distinct from the hook-point vocabulary the primitive writes per point (ADR-0020 D2) and from config overrides (`AI_HATS_USER_HOME`, `AI_HATS_LIBRARY_ROOT`, `AI_HATS_CACHE_HOME`), which carry no claim of ownership and are never treated as foreign. Three observed cross-project failures came from disagreement about this one value: HATS-897, HATS-944, HATS-1525.
- **Structural knowledge (структурное знание)** — the project root a reader derives from its **own physical anchor** — `pwd` (launcher), `dirname "$0"` under an absolute `core.hooksPath` (git-hook dispatcher), an explicitly passed `project_dir` (`paths`, `cli/githooks_hook.py`), a walk up from cwd (`cli/_helpers.py`, `ai_hats_rack.resolver`) — rather than from the environment. It decides which half of ADR-0025 D2 applies: a reader **with** it uses its own root and treats a disagreeing pin as foreign; a reader **without** it takes the pin, since that is the only statement of ownership it has. Two clauses are load-bearing. **It is determined AFTER the worktree hop** — a sub-agent legitimately runs with cwd in a linked worktree and its pin on the main checkout (that is where the tracker lives), so a reader resolving before the hop would call a valid pin foreign and write outside the tracker. And **on-disk markers are not structural knowledge**: deriving it from `.agent/` or `ai-hats.yaml` would make `self init` in an empty directory write into whichever project last exported a pin.
- **`ForeignPinPolicy`** — the caller-chosen reaction to a foreign pin. The *decision* ("is this pin foreign?") is one procedure for all callers; only the reaction is a parameter, with two values: **`REFUSE`** — the rack (`ForeignProjectPinError`), where a backlog operation under a foreign pin has no safe continuation; **`WARN_AND_IGNORE`** — the integrator, the launcher and the git-hook dispatcher, which all hold structural knowledge and can proceed on their own answer after one warning. A matching pin warns about nothing. "Ignore" means `unset`, not blanking a local variable: `githooks_run` hands `dict(os.environ)` verbatim to every gate, drop-in and chained hook, so a foreign pin left in the environment reaches all of them.

## Composition & pipeline internals

Names for the framework's composition pipeline + runtime split. Lock these in code, docs, and conversation so the "who owns the prompt" boundary stays unambiguous. Full rationale: [ADR-0005](adr/0005-composition-and-pipeline-value-contract.md).

- **CompositionResult** — the flat, immutable output of `Composer.compose(role, overlays=...)`. `@dataclass(frozen=True)`; modifications via `with_*` methods only (`with_injection_override(text)` returns a new instance). Carries `priorities`, `rules`, `skills`, `injections`, plus provenance maps (`trait_injections`, `role_injection`, `overlay_injection`).
- **CompositionPayload** — the integrator-composed bundle injected DOWN into runtime bricks (HATS-865 / ADR-0014 Composition rule). `@dataclass(frozen=True)` in `src/ai_hats/composition_payload.py` — a brick-legal leaf (it carries integrator concerns, so NOT in core; it never imports the composition layer at runtime). Fields: `result` (the ready `CompositionResult`), `provider` (resolved `Surface` instance), `effective_role`, `snapshot` (audit composition snapshot precomputed at the compose seam), `hooks` (the project's `HooksManager`), `static_cost_analyzer` (run-time-role static-cost callable threaded runner → finalize pipeline), `channel` (harness channel label for the start banner), `session_factory` / `audit_writer_factory` (HATS-867: observe writer handles — `Session` / `AuditWriter` callables threaded runner → finalize pipeline so `make_audit` never imports observe; `None` in bare payloads → make_audit contract-errors loudly), `startup_warnings` (HATS-970: hooks warnings from the first-run `set_role` side effect, surfaced by `WrapRunner` in the pre-launch read-hold instead of a bare print). Built ONCE per execution path by the **compose seam** (`src/ai_hats/composition_seam.py`) and delivered by funnel seeding (the `composition` key in `PipelineHarness.run(initial=...)`) / runner constructors — bricks never compose for prompt delivery (ADR-0005 D1).
- **Pipeline funnel** — the producer-emits / consumer-may-ignore convention by which pipeline steps thread state. Producer puts a key in the merge delta; consumer may or may not pick it up. **Value contract:** `obj is None` and `key not in ctx` are identical (the framework drops `None` values at the merge boundary); `""` / `0` / `False` / `[]` are valid non-absent values whose semantics differ from "absent". Never use magic `""` to signal "no value" — emit `None` or omit the key.
- **HITL runner** — `WrapRunner`. The human-in-the-loop runner: a user is at the keyboard, the agent runs interactively under a PTY proxy. **Has no `system_prompt_override` channel** — prompt injection is meaningless here. The role's full composition reaches the agent through the injected [CompositionPayload](#composition--pipeline-internals) + `build_session_prompt` inside `run` (HATS-865: the runner never composes).
- **Automate runner** — `SubAgentRunner`. The automation runner, with a required `task` argument. Used for sub-agent fan-out, batch / non-interactive `ai-hats execute`, and pipeline-driven spawns. **Accepts** `system_prompt_override` (HATS-267 use case — caller-supplied prompt replaces the composed injection text). Runs one of **two engines**, chosen by `Surface.engine()`: claude returns a `ClaudeSubagentEngine` and the turn happens **in-process** through `ClaudeSDKClient` (HATS-474 — bounded by `asyncio.wait_for`, finished when a `ResultMessage` arrives, so no stdout-parsing decides "is it done"); every other surface inherits the `None` default and takes the **subprocess** path (`subprocess.run` on the described argv, with a best-effort JSON parse of stdout for `response` / `usage` / `conversation_id`). Both converge on one `SurfaceRunResult` and one exit-code set — `0`, `1` (`SUBAGENT_EXIT_ERROR`), `124` on timeout (`SUBAGENT_EXIT_TIMEOUT`) — so a caller reads the outcome without knowing which engine ran. See [13].
- **Composition snapshot** — `composition_seam._composition_snapshot(assembler, role, result) -> dict` (moved from `runtime_common` in HATS-865 — it walks private Assembler API, so it computes at the compose seam and the DICT travels down in `CompositionPayload.snapshot`). Audit-only structural snapshot emitted into `Session.init_audit`. Lives in a separate channel from data-producing pipeline steps (D4 in ADR-0005) — a producer step does NOT piggyback composition data into its `produces` set for downstream routing.
- **Materialization facade** — `src/ai_hats/materialize.py`. Single derivation point for "compose role X for this project" (HATS-456 / ADR-0005 Phase 2). Wraps `assembler.composer.compose(role, overlays=assembler._get_overlays(role))` in `compose_for_role`, which since HATS-1842 is **private to this module**: consumers call a **compose purpose** (below). Every composing consumer (the HATS-865 integrator compose seam `composition_seam`, the `Assembler.set_role` writer, the carry seam `wt_effects.collect_carry_for_project`, hook-install / status / bump compose-only sites) routes through it; runners and pipeline steps no longer compose at all (HATS-865). Two drift signals are pinned by `tests/test_no_direct_compose_outside_facade.py`: a `composer.compose(..., overlays=...)` outside this module, and a `compose_for_role` call outside it. The build surface (`build_session_prompt`, `build_system_prompt`, `assemble_meta_prompt`) stays runtime-specific per D2 in ADR-0005.
- **Compose purpose** — one of six named facades in `materialize.py` — `compose_to_run`, `compose_to_install`, `compose_to_heal`, `compose_to_arm`, `compose_to_report`, `compose_to_carry` — through which every consumer reaches `compose_for_role` (HATS-1842). A caller declares what the composition is FOR; the facade decides whether a composition that lost declared content may serve it, so that policy lives once per purpose instead of once per call site. `run` / `install` / `arm` refuse; `heal` / `report` / `carry` tolerate, each for a reason recorded at its definition. The set is closed by a justified whitelist in `tests/test_no_direct_compose_outside_facade.py` — a seventh purpose is a review, not an edit.
- **Lossy composition error** — `CompositionError(message, lossy)` in `ai_hats_core.composition` (HATS-1842). `lossy=True` means the composed set is a **subset** of what was declared (a role, trait, rule or skill did not resolve); `lossy=False` means an overlay `remove` matched nothing, leaving a **superset** of intent — harmless, and tolerated since HATS-1592. The field has no default, so a new error site cannot be added without classifying it. `CompositionResult.lost` is the lossy subset, and a lossy composition raises `CompositionIncompleteError` out of `compose_for_role` unless the caller's purpose declared tolerance. The governing invariant: **a composition that lost content may never justify a conclusion of ABSENCE** — which is why `install_git_hooks` refuses to retire a dispatcher on one even when its caller tolerated the loss.

## Pipeline steps & sub-pipelines

Lock the post-HATS-535 split here. The pre-HATS-535 `launch_provider`
megastep silently hid spawn + audit + lifecycle hooks behind one
pipeline entry; the names below make the lifecycle structurally honest
in YAML and give a stable surface for tests and docs to reference.

- **`provider` step** — `Provider` (file `src/ai_hats/pipeline/steps/launch.py`). Renamed from `launch_provider` in HATS-535. Spawns the configured provider (`WrapRunner` for HITL, `SubAgentRunner` for Automate) and emits flat funnel keys `{session_id, session_dir, transcript_path, exit_code}`. **Since HATS-865 its `requires` includes `composition`** — the integrator-seeded [CompositionPayload](#composition--library); the step hands the SAME object to the runner (funnel object IS the runner object), so any pipeline using this step must seed `composition` into its initial state (see `composition_seam.build_composition_payload`). **Since HATS-867 `requires` also includes `session_mgr` and `tracer_factory`** — the CLI-seeded observe writer handles (a ready `SessionManager` + the `SidecarTracer` callable) the step threads into the runner constructors; runners no longer construct observe objects. **Does NOT publish `audit.md`** — that step moved to `make_audit`. `LaunchProvider` is retained as a deprecated class alias so externally-loaded YAMLs referencing `id: launch_provider` keep loading.
- **`make_audit` step** — `MakeAudit` (file `src/ai_hats/pipeline/steps/make_audit.py`). Sole post-spawn audit derivation surface; reads the surface's structured session log — located by the provider's own `resolve_transcript` (HATS-1087; Claude `~/.claude/projects/<key>/<claude_session_id>.jsonl`, cline `~/.cline/data/sessions/<id>/<id>.messages.json`), exact path first, then an mtime window — and rewrites `<session_dir>/audit.md` with structured turn markers (👤/👾/🔧/💭). `failure_policy = "continue"` — best-effort; the trace-log fallback in `AuditWriter` keeps audit non-empty even when JSONL is missing. **Since HATS-867 `requires` includes `session_factory` and `audit_writer_factory`** — the step constructs nothing from observe; the callables ride down in `CompositionPayload` and the runners thread them into the finalize-pipeline initial state. Shared across both HITL and SubAgent paths — closes the pre-HATS-535 asymmetry where SubAgent's `audit.md` was meta-only.
- **`compute_usage` step** — `ComputeUsage` (file `src/ai_hats/pipeline/steps/compute_usage.py`, HATS-664). Sibling of `make_audit`: same transcript source, resolved the same way (`Surface.resolve_transcript`), but emits a SEPARATE machine-readable `<session_dir>/usage.json` (`usage/v1`) instead of the human `audit.md`. The report carries measured always-on (first `cache_creation` proxy), an ordered event timeline (skill-body loads, reference Reads, tool calls, stop-hook firings), aggregates with tool success-rate, sidechain linkage, and the ai-hats session metadata (`role` / `provider` / `exit_code`) the step copies from `metrics.json` so the report self-describes which composition produced this cost (the comparison sibling pairs sessions by role; "what went wrong" debugging reads it without a second lookup). When `role` resolves, the step also attaches a static `costs.py` per-component always-on breakdown under `always_on.static` for measured-vs-static cross-check. Heavy lifting is the pure `parse_session_usage` in `packages/ai-hats-observe/src/ai_hats_observe/usage.py` (transcript-only, fail-soft, also runnable as `python -m ai_hats_observe.usage <jsonl>` for retroactive sweeps), reached through the surface parser (`ClaudeParser.parse_usage`) since T15/0.3.0; the step is the thin live driver that resolves the JSONL, optionally enriches always-on with a static `costs.py` cross-check when `role` is in the funnel, and persists. `failure_policy = "continue"`. Used in BOTH `finalize-hitl` and `finalize-subagent`, positioned right after `make_audit`. Token attribution per event is a documented `reconstructed` heuristic (per-message usage is a per-turn total) — unattributable events keep `tokens_delta = null`, never a magic `0`. HATS-734: the discovery fallback keys off the ai-hats `session_id` (the `claude_session_id` `uuid4` never parses the `strptime` window, so before the fix it was dead in `--resume`/`--continue`), and `usage.json` gained its first reader — the Usage section of `ai-hats session show`.
- **`maybe_spawn_session_reviewer` step** — `MaybeSpawnSessionReviewer` (file `src/ai_hats/pipeline/steps/maybe_spawn_session_reviewer.py`). Auto-retro decision + spawn block extracted from `RunSessionEnd` in HATS-530 so HITL and SubAgent pipelines can share a single source of truth. Runs `make_decision` + `write_retro_log`; when `action == "run"` and `HATS_SKIP_RETRO != "1"` fires `_spawn_session_reviewer_background`. `failure_policy = "continue"`. Produces `retro_decision: dict` so a downstream step (HITL's `run_session_end` banner) can render user-visible context without re-deciding. Used in BOTH `finalize-hitl` and `finalize-subagent`.
- **`run_session_end` step** — `RunSessionEnd` (file `src/ai_hats/pipeline/steps/run_session_end.py`). HITL-only finalize stage: the cyan retro reminder banner. Reads `retro_decision` (optional) produced upstream by `maybe_spawn_session_reviewer`; absent the key the banner is silently skipped. Pre-HATS-530 this step also owned the retro decision/spawn block — extracted to `maybe_spawn_session_reviewer` to close the HITL/SubAgent asymmetry. It also dispatched `SESSION_END` lifecycle hooks until HATS-707 deleted the dead `hooks:` composition channel (zero runtime consumers). `finalize-subagent` intentionally omits this step (SubAgent has no TTY for the banner).
- **`finalize-hitl` sub-pipeline** — `library/core/pipelines/finalize-hitl.yaml`. Steps: `make_audit → compute_usage → maybe_spawn_session_reviewer → run_session_end`. Invoked by `WrapRunner.run` from its `finally` block via `PipelineHarness`-equivalent `pipeline.run(...)`. `claude_session_id` passes via `initial=` kwargs (NOT through the main `human` pipeline funnel) so the runner-private state stays out of the public funnel surface.
- **`finalize-subagent` sub-pipeline** — `library/core/pipelines/finalize-subagent.yaml`. Steps: `make_audit → compute_usage → maybe_spawn_session_reviewer`. Invoked by `_finalize_sub_agent` when `work_dir` + `claude_session_id` are both available (the single-turn `_run_attempt` path). HATS-530 added `maybe_spawn_session_reviewer` here so SubAgent sessions trigger auto-retro under the same threshold/policy as HITL. `run_session_end` is still intentionally absent (no banner for SubAgent — no TTY).

## Session-end output blocks

Two visually similar blocks fire at the end of a [Session](#session). Use these names in code, docs, and conversation — calling both "плашка" or "banner" hides the distinction.

## Git-hook surface

The `.githooks/` tree — **generated by composition, not tracked in git**. Since HATS-1337 it holds exactly one kind of file: the per-event dispatcher. Gate *content* stays in the declaring skills and is resolved at commit time (ADR-0020 D3).

- **Orchestrator** — the durable artifact `ai-hats init` installs: a `.githooks/<event>` dispatcher per declared event, plus an absolute `core.hooksPath`. It carries no role logic and no path into a versioned venv, so it survives `self update` by content — the next commit runs the new version's gates with no re-materialization step (M12).
- **Dispatcher stub** — `.githooks/<event>`, written from `src/ai_hats/templates/githooks/dispatcher.sh` and marker-guarded by the `AI-HATS-DISPATCHER-MARKER` comment it carries (a foreign hook of the same name is left alone; the marker is also what proves ownership for removal, since no manifest exists). Deliberately a **stub**: it resolves an interpreter and `exec`s a six-line bootstrap that imports `ai_hats.cli.githooks_hook` and calls `main(...)` with the event, the project root, its own directory and git's hook arguments. It imports rather than running `-m` on purpose: `-m` exits 1 on an ai-hats too old to carry the module, and under `exec` that 1 would become the hook's verdict — version skew would BLOCK the commit instead of skipping the gates. Which gates run, in what order, how stdin is replayed, whether a drop-in or the previous hook manager is chained — none of that is in the file, because it is **not rewritten at commit time** (`tests/e2e/test_githooks_orchestrator.py:170-180` pins exactly that) and between two `ai-hats self …` runs the bytes already on disk are what execute — so everything it contains is a contract with every project composed inside that window, which spans years. It *is* re-copied whenever ai-hats re-materializes the project: `_install_dispatcher` (`src/ai_hats/hooks_manager.py:252-266`) does an unconditional `shutil.copy2` over any file still carrying the marker, driven by `self init` / `self update` / `set_role` through `Assembler._refresh`. A stub a human edited into losing its marker is left alone forever. The two jobs it cannot delegate: bootstrap an interpreter, and fail open when there is none.
- **Fail-open degradation (stub only)** — an ai-hats the stub cannot resolve or import skips the gates with one warning line and lets the commit through. A human `git commit` is never wedged; the pre-1337 fail-closed backstop refused the event and prescribed `ai-hats self init`, the one command needing exactly the absent binary. A *module* is spawned rather than the `githooks resolve` subcommand precisely so version skew degrades this way: an unregistered subcommand would be treated as a bare prompt and launch a provider session (`_PassthroughGroup`, HATS-1202). **Scope narrowed by HATS-1828** — this now names the stub alone, because its basis is that the bytes on disk cannot be repaired at commit time. Once the entry point is executing, ai-hats is present and `self update` reaches it, so the next entry applies.
- **Delivery refusal (dispatcher)** — once `githooks_hook.main` runs, a gate ai-hats cannot DELIVER stops the git operation instead of passing it: unparsable dispatcher arguments, an untrusted session envelope, a failed composition, a gate the resolver rejected, an `execve` that failed, or a script that exceeded its budget. What unites them is not one verdict class — four never reach a `HookRun` at all, an `execve` failure is `CORRUPT` and an expired budget is `BROKE` — but the fact behind it: the gate never produced a verdict, so there is none to defer to (ADR-0020 D2). The channel therefore branches on `HookOutcomeKind`, never on `HookVerdict`: `BROKE` is the downgradable class and also holds plain `exit 1`, so a policy hung on the verdict would disarm every git gate at once. A gate that DID run and exited non-zero is untouched: that is its author's verdict, and it propagates as git's own contract says. Every refusal must name the flag that opens it, or it merely manufactures `--no-verify`, which disarms the whole chain (HATS-1828; the invariant is pinned for the tool-call chain by `test_every_deny_names_its_hatch`).
- **`AI_HATS_GIT_GATE_BROKEN_ACK`** — the delivery hatch. Set to `1` to turn a delivery refusal back into a recorded skip, so the commit that REPAIRS a broken gate is not blocked by the gate it repairs. Every use lands in the bypass journal, where `pre-push-bypass-report.sh` surfaces it at push. Withheld from sub-agents by shape (`BYPASS_FLAG_SUFFIXES`): the hatch is a person's, not an agent's.
- **`AI_HATS_GIT_HOOK_TIMEOUT_S`** — per-script budget for the git chain, default 900 s, applied to gates, drop-ins and the chained pre-takeover hook alike. Deliberately generous: a `pre-commit` running a test suite is not a hang, and the bound exists for the caller who cannot press Ctrl-C — CI, cron, an agent session. A non-numeric or non-positive value falls back to the default, so a typo cannot disable the bound. Expiry is a script problem, not a delivery one, so it refuses and points here rather than at the delivery hatch.
- **`AI_HATS_BYPASS_JOURNAL`** — absolute path to `bypass_journal.sh`, exported by the dispatcher because a gate running in place cannot reach it relatively from every library root. Gates source `"${AI_HATS_BYPASS_JOURNAL:-$(dirname "$0")/../../../../hooks/bypass_journal.sh}"`.
- **`<event>.d/` drop-in** — read, never written. ai-hats materializes nothing there; a script a human drops in still runs (after the resolved gates), and nothing sweeps it.
- **Managed-hook drift net** — *retired* (HATS-1480). The session-start check (`Assembler.sync_hooks`, HATS-833) re-materialized any drifted managed-hook surface. It existed to police the shared managed copies; those are gone — `lifecycle_hooks` (HATS-1147), `library/wt-hooks/` (HATS-1269), `library/hooks/` (HATS-1480) — and git never had a gate set to drift from (HATS-1337). With no surface left to detect or heal, the net was removed rather than left reporting on nothing.

## Tool-call hook channel

How a composed runtime hook reaches an agent's tool call. The sibling of the git-hook surface above: same primitive, different arrival. Four surfaces run it in-process today (agy, cline, codex, opencode); **claude has a channel and is not yet wired to it** (HATS-1868) — its hooks are still executed by the harness from a materialized `settings.json`, which runs them fail-open by contract: a gate whose script has vanished, or one killed by its own timeout, lets the call through with `rc=0` and nothing on stderr. That is what owning the execution buys, and the cutover waits on HATS-1869 for its latency budget.

- **Matcher vocabulary** — the names a `SKILL.md` matcher is written in (`Bash`, `Edit|Write|MultiEdit`). It belongs to no surface: a surface whose native names already spell it needs no translation, which is not the same as owning it. Every other surface maps into it.
- **Surface channel** — `SurfaceChannel` in `src/ai_hats/surfaces/hook_dispatch.py`: the four things only a surface can answer — how a call **arrives** (`Arrival`: its own event name, and which bindable event that is), where its composed **rows** come from, how the stdin document **reads** as calls, and how the verdict is **emitted** as its own document. `dispatch()` is the order those four go in, and holds everything between them in one copy: the delivery refusal, the reduction, the chain, the stderr relay. What a surface can UTTER and what status it EXITS with are deliberately NOT answers — both are known before a hook arrives, so both are rows of **Surface profile** (`speaks` / `speaks_on`, `imposed_status` / `forwards_hook_status`) and the status is derived from the verdict by `status_for`. claude is the first implementation (`src/ai_hats/surfaces/claude/channel.py`); `tests/test_surface_channels_go_through_dispatch.py` refuses a channel that calls `run_chain` / `reduce_to` / `undeliverable` / `relay_stderr` itself, with the four hand-written dispatchers as its positive control, and HATS-1871 moves them over.
- **Surface profile** — `SurfaceProfile` in `src/ai_hats/surfaces/hook_channel.py`, one frozen row per surface, each kept beside its own surface (`src/ai_hats/surfaces/<name>/profile.py`) and gathered by `src/ai_hats/surfaces/profiles.py`. It carries names and paths and no branch of policy: native tool names, native argument names, where the manifest sits, where the skills mirror sits, the dialect the surface speaks — per arrival where one surface narrows it (`speaks_on`, codex on `PermissionRequest`) — and which exit status a refusal earns (`imposed_status`, `forwards_hook_status`). A hole in a row is how a whole class of gates goes quiet on one surface while every test stays green — codex had no terminal row at all, so `safety_gate.py` never matched its shell.
- **Bindable events** — `BINDABLE_EVENTS`, derived from the `HookEvent` enum, which is pinned equal to `RUNTIME_HOOK_EVENTS`. A surface states the events it will actually deliver in its profile's `native_events` — usually exactly this set, plus its own arrivals where it has any (codex's `PermissionRequest`). A test refuses a surface whose row does not cover every bindable event, so adding one cannot be half-done: a hook bound to it would compose fine and never fire.
- **Reduction** — one thing a surface cannot utter and what it becomes instead, held in a table (`REDUCTIONS`) and applied to a **fixed point** rather than in sequence. One reduction can produce what another must then handle — a refusal that becomes a nudge on a surface that also cannot carry nudges — and an if-chain gets that right only in the order it happens to be written. The order-independence is a property a test checks by handing `reduce_to` a permutation, which is why the order is a parameter.
- **Dialect** — what a surface can utter natively: put a question at all, carry that question together with the rewritten input, cancel a call that already ran, carry a nudge onward. A verdict a surface cannot utter is reduced once, in the channel, so the wording exists in one copy.
- **Matched gates run together** — every row a call matches is started at once, bounded by `HOOK_PARALLELISM`, and the verdict is drawn afterwards by walking the rows in order. Two halves, and only one of them changed: the chain still reports the FIRST objector in row order, so a refusal reads exactly as it did. What changed is which gates RUN — one behind an objector now does, so a gate with a side effect (the bypass journal, `py_security_lint`) fires where it used to be skipped, and its stderr is carried with the rest. The chain answers in max-time rather than sum-time, which is what claude's own hook runner does (measured on 2.1.247: three 0.5 s hooks, 0.511 s wall) and what a dispatcher standing in for it has to match. Execution order among matched gates stopped being observable, which is why four e2e ledgers compare a set.
- **Chain verdict** — `ChainVerdict`, what the whole composed chain concluded for one call: the decision, the reason, the deciding hook, the nudges, a rewritten input, the child's stderr, and the hatch. One value, whether it is returned in-process or marshalled as a document to a channel that cannot hold it (`to_wire`).
- **Nudge** — non-gating advice a hook fed back (`additionalContext`). Carries its author, because a chain joins nudges from several hooks and joined text cannot say whose advice it is.
- **Consent ticket** — a question and a rewritten command in ONE reply: `safety_gate.py` mints a nonce, prefixes the command with it, and answers `ask` plus `updatedInput` together. A surface that can ask but cannot carry the rewrite would show the human the ORIGINAL command, so the two travel as one capability and a ticket that cannot follow turns the question into a refusal.
- **Delivery refusal** — a gate ai-hats could not DELIVER refuses the call and names the way past it, rather than passing it with a line on stderr. What unites the cases is not one verdict class but the fact behind it: no verdict was ever formed. It happens at two levels — one hook that would not start, and a manifest that never resolved — and both go through one constructor so all four surfaces answer the same way. A gate that DID run and refused is its author's verdict and carries no hatch of ours.
- **`AI_HATS_HOOK_TIMEOUT_S`** — the budget for the whole chain of one tool call, default 60 s, drawn through one deadline so a slow gate cannot quietly starve the ones behind it. Where a surface imposes an outer bound on the dispatcher at all, it is derived from this with a margin rather than written by hand: bounding both at the same number is what made codex's every timeout branch unreachable and left a killed chain with no verdict. Two surfaces have one — codex writes it into its TOML, opencode is handed it through `AI_HATS_HOOK_SURFACE_TIMEOUT_MS` because its plugin is copied verbatim; agy and cline impose none, so their dispatcher is bounded from the inside only, which is the direction that leaves it alive to answer. `AI_HATS_AGY_HOOK_TIMEOUT_S` was this bound while only one surface of four offered it; it is still honoured and says so once per process.
- **`AI_HATS_GATE_BROKEN_ACK`** — the delivery hatch for this channel, the sibling of `AI_HATS_GIT_GATE_BROKEN_ACK` and read the same way: beside the refusal it opens, so a deny always names a flag that works (HATS-1253 P4). It covers a gate that could not be MATERIALIZED — one hook that would not start, or a manifest that never resolved — and never a timeout, which has its own bound to raise, nor a refusal a hook itself uttered. Taking it is recorded on stderr and in the bypass journal; passing a gate is allowed, passing one silently is not. Withheld from sub-agents by shape: the hatch is a person's, not an agent's.

## Command lifetime

Nothing bounds how long a shell command launched on an agent's behalf stays alive (HATS-1873). The harness's own budget does not close the hole: a foreground Bash call that exceeds its timeout is *moved to the background*, not stopped, and `bounded_proc_shutdown` (`src/ai_hats/pty_shutdown.py`) reaps the provider's process group only when the session ENDS. Both are correct and neither fires in a long-lived session — which is the session a person is sitting in front of. Field evidence: three wait-loops, 21 h 25 m alive, 83 min of CPU between them, found by hand in `ps`.

- **`command-lifetime`** — the core skill carrying the gate, and the reason it is not folded into `tool-call-hygiene`: that guard's contract states it never emits a `permissionDecision`, so a refusal cannot live there without contradicting the file's own header.
- **Unbounded loop** — a `while` / `until` whose exit is not bounded by anything the guard can see: no `timeout` wrapper, no iteration counter. The predicate is structural, not lexical, and that is the point — `run_in_background` cannot stand in for it, because the flag describes what the agent ASKED for while auto-backgrounding happens after the hook has already answered. A guard built on the flag alone would pass its tests and still miss the incident that opened the card.
- **`pre_bash_lifetime_guard.sh`** — the PreToolUse Bash hook. Refuses an unbounded loop and an unbounded background launch; NUDGES, never refuses, on a merely long-running command, because a deny that cries wolf on routine work gets switched off and a switched-off gate is worth less than the nudge it replaced.
- **`AI_HATS_LIFETIME_ACK`** — the hatch for a deliberately long-lived process, spelled `_ACK` rather than `_OFF` by the same split the rest of the library keeps: `_OFF` silences advice (`AI_HATS_TOOL_HYGIENE_OFF`), `_ACK` answers a refusal (`AI_HATS_DESTRUCTIVE_ACK`). Like every PreToolUse hatch it must be in the environment that LAUNCHED the agent — the guard runs before the command it judges is a process, so a per-command prefix never reaches it.
- **Why the guard does not supply the bound** — it could: `updatedInput` is a real capability here, and the consent ticket above already answers `ask` plus a rewrite in one reply. The guard still refuses instead of wrapping, so the number in `timeout N` is one the agent chose and exit 124 means a budget somebody set. A bound the agent never picked produces a 124 nobody can interpret.

## Safe-delete trash bin

Single point of truth for destructive filesystem ops in ai-hats core (HATS-470). Replaces the historical pattern of raw `path.unlink()` / `shutil.rmtree()` / in-place `path.write_text(new)` calls.

- **`ai_hats_core.safe_delete`** — module exposing `discard(path, *, reason, project_dir)`, `replace(path, new_content, *, reason, project_dir)`, `session_summary()`, `session_root()`, `reset_session()`, plus `TrashFullError`. `discard` moves a file/dir/symlink to the current trash session; `replace` snapshots the old content to trash, then atomic-writes the new bytes. Symlinks are unlinked (link only — target preserved, original target written to a sidecar `.symlink` file).
- **Trash session directory** — `${TMPDIR:-/tmp}/ai-hats/trash-<utc-ts>-<pid>-XXXXXX/`. One per process, lazily created on the first destructive op; `tempfile.mkdtemp` guarantees uniqueness across concurrent ai-hats invocations. Contents mirror the project-relative path of each victim, plus a `MANIFEST.md` recording every op (timestamp, kind, reason, original → trash path). External-to-project paths land under `_external/<abs-tail>/`. Recovery: `cp -r <session>/<rel> <project>/<rel>`. **Not auto-cleaned** — relies on OS `/tmp` retention.
- **`AI_HATS_TRASH_DIR`** — env var. Overrides the trash base directory (the `trash-<ts>-<pid>-XXXXXX/` subdir is still created underneath). Special sentinel `AI_HATS_TRASH_DIR=-` enables **hard-delete mode**: no snapshots, one WARN to stderr per op, no session directory. Intended for CI / ephemeral environments where snapshot value is zero.
- **`TrashFullError`** — `OSError` subclass raised when the snapshot can't land (ENOSPC, read-only filesystem, missing permission). Callers (bump / init) treat it as fatal — partial migrations without a recoverable snapshot violate the trash-bin contract.
- **Inline whitelist marker** — `# safe-delete: ok <reason>` on the same line as a raw `unlink` / `rmtree` / `rmdir`. Use only for genuinely safe cases (empty-dir cleanup, internal `.tmp` from atomic-write, session-cache rebuild, framework-managed manifest). Enforced by the `pre-commit-no-raw-destructive.sh` hook in the `git-mastery` skill — refuses commits that introduce raw destructive ops without either being in `src/ai_hats/safe_delete.py` or carrying the marker. Override: `AI_HATS_NO_RAW_DESTRUCTIVE_SKIP=1 git commit ...`.
