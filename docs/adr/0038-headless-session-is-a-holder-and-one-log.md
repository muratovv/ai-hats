# ADR-0038: Headless-сессия — фильтр над бинарём surface'а: stdin внутрь, stdout наружу, один журнал на все режимы

## Статус

Принят (HATS-2019, 2026-09-21). Поправки: HATS-2020 — граница хода `TurnEnded`,
флаги провода у holder'а; HATS-2028 — провод как единственный источник событий
основного агента, кодек surface'а в обе стороны, id промпта; HATS-2029 — один
producer на факт во всех режимах (D4), состояние сессии по якорю (D7), отказ по
readiness и коды выхода (D11).

Пишущая половина того, что ADR-0037 оставил открытым: «ответить на вопрос,
разрешить вызов, прервать ход — это *команды*, отдельный контракт». Читающая
половина — канонические события и живой `events.jsonl` — уже стоит; здесь
решается, как команда доходит до бинаря, какой процесс держит бинарь и как
клиент узнаёт, что сессия кончилась.

## Контекст

ai-hats запускает surface двумя способами, и до последнего шага они одинаковы:
композиция роли → `SessionRun.create` → `plan_session` → `apply` → захват кэша →
`LaunchFlags` → `launch` → `init_audit`. Расходятся они только в том, что
держит бинарь: `WrapRunner` — PTY и терминал человека, `SubAgentRunner` — SDK
с одним промптом и ожиданием `ResultMessage`. Ни один из двух не принимает
второй ход от программы, не отвечает на вопрос о разрешении не из терминала и не
отдаёт свои события потоком.

Читающая сторона уже провайдер-нейтральна: `events.jsonl` (`events/v1`) пишется
во время сессии, его словарь назван по обязательству потребителя (ADR-0037),
и среди названных потребителей стоит «headless-контроллер».

Что **измерено** на живом бинаре (claude 2.1.278, [1]). Бинарь в режиме
`--input-format stream-json --output-format stream-json` — это уже обычный
UNIX-фильтр: одна JSON-строка на ход внутрь, одна на событие наружу, граница
хода — событие `result`. Закрытие stdin означает «ввода больше не будет»: два
хода, записанные подряд, после чего пайп закрыт, бинарь отрабатывает оба
(`result_index` 0 и 1) и выходит с кодом 0. Вопрос о разрешении приходит в
stdout строкой `control_request` (`can_use_tool`) и ждёт `control_response` в
stdin. Сессия, начатая с `--session-id`, продолжается из другого процесса по
`--resume <id>`. Всё это работает без SDK, без `-p`, без рукопожатия
`initialize`, без диалога доверия к папке и — как интерактивная сессия — на
подписке: ключа в среде нет, `HOME` наследуется, `apiKeySource: "none"`, расход
виден окнами `five_hour` / `seven_day` в `rate_limit_event`. `total_cost_usd` в
`result` — расчётная оценка при любом способе оплаты, а не счёт.

Два места, которые решение сначала приняло по исходникам SDK, замерены
позже на 2.1.281 ([1], §10). Первое — `interrupt` как `control_request` и то,
каким событием он закрывает ход. Второе — форма argv HITL (`--system-prompt-file`,
`--plugin-dir`, `--settings`) поверх stream-json. Argv настоящей роли работает
на проводе, хуки из `--settings` срабатывают.

Что отвергнуто по замерам, а не по вкусу:

- `claude --bg` / `attach` / `logs` (HATS-1968): у фоновой сессии нет глагола
  для инъекции хода (только stop → resume), `--bg` несовместим с `-p`, `logs`
  отдаёт ANSI, а не запись.
- ACP как внешнее API: один клиент на процесс агента, второго клиента к живой
  сессии протокол не подключает; Microsoft AHP описывает мультиплексор как
  «mutex поверх ACP» — то есть слой над агентом нужен *и* при ACP.
- Сокет и любой сервер внутри ai-hats: второй протокол и весь fan-out relay
  заново (HATS-1193: bounded-очереди, seq-ring, eviction).
- `ClaudeSDKClient` в holder'е: прячет pid ребёнка (якорь liveness), ставит
  между нами и бинарём слой, который мы не контролируем; провод уже доказан
  сырым. Мы оборачиваем харнесс, а не его SDK.
- Журнал как очередь команд с несколькими писателями (ранние редакции этого
  ADR): отдельный писатель команд, хвост, исполняющий записи, признаки
  завершения в двух файлах, визитка для опоздавшего клиента — всё это нужно
  было только ради второго писателя, и всё это исчезает, если писатель один.

Решения супервизора, из которых растут разделы ниже: бинарь, не SDK; журнал
один и общий для всех режимов; все данные сессии — через stdin/stdout; процесс
и есть сессия — кончился процесс, кончилась сессия; несколько писателей садятся
**сверху** headless, а не внутрь него.

## Решения

### D1 — четыре термина, и они закреплены в глоссарии раньше кода

**Headless-сессия** — сессия без терминала: бинарь под тем же argv, что и
интерактивный, но со структурным потоком вместо PTY. **Holder** — процесс
`ai-hats headless`, который владеет бинарём, журналом и своими stdin/stdout.
**Команда** — строка на stdin holder'а. **Заголовок сессии** — первая строка
его stdout: кто эта сессия и где лежит её журнал; то, что исходная постановка
называла «кредами». Определения — в [2]; документ использует ровно эти
написания.

### D2 — holder — фильтр: один писатель на stdin, поток на stdout, выход процесса — конец

Контракт целиком — три потока и код выхода, как у любой UNIX-программы:

| Поток      | Что в нём                                                                        | Кто                               |
| ---------- | -------------------------------------------------------------------------------- | --------------------------------- |
| stdin      | команды (D3), по одной JSON-строке                                               | один писатель — тот, кто запустил |
| stdout     | строка 1 — заголовок (D9), дальше — копия журнала `events.jsonl` с первого байта | holder                            |
| stderr     | всё человекочитаемое: баннеры, заметки, ошибки                                   | holder                            |
| код выхода | исход сессии (D11)                                                               | holder                            |

Писатель один. Holder не сериализует нескольких клиентов, не держит их очереди
и ничего не знает о том, кто стоит за его stdin. Нужны несколько писателей —
relay, веб-клиент, редактор и скрипт одновременно — их объединяет мультиплексор
**над** holder'ом, который сам владеет его stdin и stdout: HAI строит именно
такой слой. Внутрь headless этот вопрос не проникает.

stdout — копия журнала, а не отдельный поток: holder читает `events.jsonl` с
первого байта и пишет в stdout каждую полную строку, как только она там
появилась. Поэтому то, что видит родитель, и то, что потом прочитает любой
другой, — одно и то же, в одном порядке; разойтись им нечем.

### D3 — три команды, и каждая переводится в действие на проводе по таблице surface'а

Формат команды — одна JSON-строка своей версии; в журнал команды не пишутся
(D4):

```json
{"v":"commands/v1","cmd":"prompt","id":"<UUID, необязательно>","text":"…"}
{"v":"commands/v1","cmd":"answer","call_id":"<из person_asked>","decision":"allow"}
{"v":"commands/v1","cmd":"answer","call_id":"<из person_asked>","decision":"deny","message":"…"}
{"v":"commands/v1","cmd":"interrupt"}
```

Глаголы названы по тому, что должен сделать holder (ADR-0037 D1), а не по слову
surface'а. Отдельной команды `stop` нет: остановка — это EOF на stdin или
сигнал (D11). Нового глагола словарь не получает, пока у него нет второго
producer'а или живого consumer'а — правило D4 ADR-0037.

Таблица для claude:

| Команда      | Действие на проводе claude                                                                                                                                                                                                                                                                                                                                                              | Что появляется в журнале                                                                   |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `prompt`     | строка в stdin: `{"type":"user","message":{"role":"user","content":<text>},"parent_tool_use_id":null,"session_id":"default","uuid":<id>}`                                                                                                                                                                                                                                               | `PromptReceived(prompt_id)` из эха провода, события хода, `TurnEnded(prompt_ids)`          |
| `answer`     | строка в stdin: `{"type":"control_response","response":{"subtype":"success","request_id":<из control_request>,"response":{"behavior":"allow","updatedInput":<input>}}}` — или `{"behavior":"deny","message":…}`                                                                                                                                                                         | `ToolResultReceived`; `GateVerdict`, если решила цепочка гейтов                            |
| `interrupt`  | `{"type":"control_request","request_id":<новый>,"request":{"subtype":"interrupt"}}`. Сразу приходит `control_response` `{"still_queued":[…]}`; идущий ход закрывается `result` с `subtype: error_during_execution`, `terminal_reason` `aborted_streaming` (генерация) или `aborted_tools` (инструмент — его процесс убит); без хода — ничего; следующий `prompt` принимается ([1], §10) | `Notice(interrupted)`, прерванный ответ закрыт `ResponseEnded` (`cancelled` при генерации) |
| EOF на stdin | на открытый `can_use_tool` ответить deny, затем закрыть stdin ребёнку. Он доделывает принятые ходы и выходит. Вопрос, заданный после EOF, бинарь отклоняет сам, и модель тратит на него попытки. Фоновые задачи бинаря останавливаются ([1], §10)                                                                                                                                       | события оставшихся ходов, затем `run_ended`                                                |

Обратный поток: `control_request` с `subtype: can_use_tool` holder переводит в
`PersonAsked(kind=permission, call_id=<tool_use_id>, tool=<tool_name>,
source="claude/wire")` и ждёт `answer` с этим `call_id`, не переставая читать
stdout ребёнка. Если `PersonAsked` с этим `call_id` в журнале уже есть, holder
второй не пишет. Вопрос гарда роли (`decision_reason_type: "hook"`) диспетчер
записывает сам, ещё до того, как вопрос выходит на провод ([1], §10.1). Один
факт — один producer. `control_cancel_request` с `request_id` вопроса значит, что
бинарь отозвал вопрос сам (interrupt при открытом вопросе). Holder закрывает
ожидание, и `answer` на этот `call_id` дальше — уже закрытый.

Правила, без которых реализация неоднозначна:

- `prompt` во время идущего хода уходит на провод немедленно. Очередь держит
  бинарь, holder не буферизует. Что станет с промптом, решает бинарь: claude
  2.1.281 вливает промпт, пришедший до границы инструмента, в идущий ход, и оба
  промпта закрывает один `result`, а значит, один `TurnEnded` с id обоих в
  `prompt_ids` (замер HATS-2028). Промпт, пришедший посреди генерации без
  инструмента, ждёт: его ход начинается после текущего.
- Почему очередь не у holder'а (супервизор, HATS-2020). Что делать с ходом,
  присланным посреди другого, решает surface, и вливание в идущий ход — поведение
  самого claude. Holder, который держал бы очередь сам, тихо поменял бы это
  поведение.
- Порядок журнала — порядок провода (поправка HATS-2028). События основного
  агента holder берёт из одного потока — stdout бинаря (D4). Поэтому
  `PromptReceived` хода N+1 стоит после `TurnEnded` хода N всякий раз, когда бинарь
  начал ход N+1 после `result` N, как бы рано ни был послан промпт.
- Свой ход клиент находит по id, а не по счёту. `id` у `prompt` необязателен; без
  него holder чеканит uuid4 сам, так же как для позиционного промпта. Клиент ждёт
  `turn_ended`, в `prompt_ids` которого есть его id. Считать `turn_ended` нельзя:
  вливание закрывает два промпта одной строкой, а ход, начатый бинарём, — ни
  одного.
- `id` — UUID в каноническом виде (`str(UUID(id)) == id`), новый для сессии.
  Иначе — `command_rejected`. claude принимает в `uuid` любую строку, а повтор
  молча выкидывает, но эхо шлёт (замер HATS-2028): клиент, повторивший id, ждал
  бы вечно.
- на один `call_id` побеждает первый `answer`; второй, как и `answer` на
  неизвестный или уже закрытый `call_id`, и строка, которую holder не смог
  прочитать, дают `Notice(reason=command_rejected, raw_code=<cmd>,
  detail=<почему>)`. Это новая причина в `WorthRecording`, и её consumer живой —
  клиент headless (правило D4 ADR-0037); `unsupported_record` остаётся за
  дрейфом схемы (ADR-0037 D5).
- `request_id` и исходный `input`, нужные для `control_response`, живут только
  в памяти holder'а; сколько он ждёт `answer` и что делает по истечении — режим
  разрешений, он объявляется ролью и решается в HATS-2021.

Таблица — контракт surface'а: другой surface приносит свою (у `agy` тот же
stream-json с другим конвертом, у codex — `app-server`, у gemini и cline — ACP),
словарь команд не меняется.

**Таблицу исполняет кодек surface'а** (поправка HATS-2028). Команды и события —
наши объекты: `Prompt(text, id)` и кодек `commands/v1` лежат в `ai_hats_observe`
рядом с событиями. Формат claude живёт только в `ClaudeWire`, в обе стороны:
`encode(command)` даёт строку stdin бинаря, `decoder()` переводит строку его
stdout в события. Holder перекачивает объекты между двумя кодеками и слов
surface'а не видит. Другой surface приносит свой кодек, а holder и клиент не
меняются.

**Флаги провода принадлежат holder'у** (поправка HATS-2020). В остальном holder
принимает те же параметры, что голый `ai-hats`. Флаги, из которых складываются
провод и запись сессии, holder ставит сам и принимать от вызывающего
отказывается: выход 2 до старта, заголовка нет. Это `--input-format`,
`--output-format`, `--print`, `--permission-prompt-tool`, `--resume`,
`--continue`, `--session-id` и `--no-session-persistence`: без записи на диске
журналу нечего читать.

- `--permission-prompt-tool stdio` — это то, как вопросы бинаря попадают к
  holder'у, а не настройка пользователя. Без команды `answer` ход с этим флагом
  висел бы вечно, поэтому первый трассер его не ставит, а ставит всегда задача с
  `answer`.
- Настройка пользователя — политика «какие вопросы доходят до владельца»
  (HATS-2021).

Ещё три флага holder ставит всегда, но от вызывающего их не отклоняет — повтор
безвреден (поправка HATS-2028):

- `--replay-user-messages` — эхо промпта с его id; без него провод не говорит,
  когда ход промпта начался;
- `--include-partial-messages` — итоговые `usage` и `stop_reason` ответа есть на
  проводе только в `message_delta`: без флага `output_tokens` там 1–4;
- `--include-hook-events` — сбои хуков и Stop-хуки, которые иначе есть только в
  записи.

### D4 — журнал один, `events.jsonl`, формат общий для всех трёх режимов и не меняется

У сессии один журнал — `<session_dir>/events.jsonl` (`events/v1`, 0600,
append-only), тот же, что у `ai-hats` и `ai-hats agent`. Headless добавляет в
него один вид записи — `TurnEnded`, конец хода (D10; поправка HATS-2020) — и два
поля: `PromptReceived.prompt_id` и `TurnEnded.prompt_ids` (поправка HATS-2028).
Оба направления в нём уже есть — ход, отправленный командой `prompt`, приходит
как `PromptReceived` с `origin: harness`, ответ на вопрос виден как
`ToolResultReceived`. Потребителю журнала не нужно знать, каким режимом сессия
была запущена.

**В headless события основного агента берутся с провода** (поправка HATS-2028).
Поток, читающий stdout бинаря, — единственный producer событий основного агента:
кодек surface'а переводит строку провода в события, и holder пишет их через
писатель журнала. Запись основного агента в headless не хвостится; в PTY её
ридер — по-прежнему единственный producer. У ридера claude поэтому два входа —
файл и строка провода — и один разбор (ADR-0037).

Записи сабагентов хвостятся, как в PTY: на проводе нет ни финального ответа, ни
thinking сабагента (замер HATS-2028). Порядок их событий не гарантирован ни
относительно основного агента, ни внутри цепочки сабагента. Вердикт хука сабагента
может встать раньше его вызова.

Сверх того, что приносит провод, holder производит:

- `PersonAsked(permission)` из входящего `control_request` — запись узнаёт о
  вопросе только после ответа;
- `Notice(command_rejected)` из D3;
- `TurnEnded` — на каждом `result` провода (D10);
- `Notice(unsupported_record)` на строку провода, которую не прочитать: не JSON
  (`malformed-json`) или сбой декодера (`decoder-error`). Незнакомый вид строки
  говорит сам ридер (поправка HATS-2029).

**Один факт — один producer** (поправка HATS-2029). Producer факта — источник,
который ридер видит на обоих входах, в записи и на проводе: тогда журналы PTY и
headless совпадают по построению. Источник, который есть только на проводе,
берётся лишь для факта, у которого в этом режиме другого источника нет.

| Факт                                       | PTY (`ai-hats`)                                      | headless                                                                                                                                                 | Automate (`ai-hats agent`, SDK до HATS-2022) |
| ------------------------------------------ | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| события основного агента                   | запись                                               | провод                                                                                                                                                   | запись                                       |
| стена квоты, `HarnessActionRequired(wait)` | ошибка API в записи, время снятия — её `quotaLimits` | ошибка API на проводе; время снятия — из последнего `rate_limit_event` `rejected`: у ошибки на проводе поля квоты нет (схема stream-json claude 2.1.282) | ошибка API в записи                          |
| `Notice(approaching_limit)`                | статуслайн                                           | `rate_limit_event` `allowed_warning`: статуслайн под stream-json не запускается (замер HATS-2029)                                                        | SDK-поток                                    |
| отказ инструмента                          | `is_error`-результат в записи                        | тот же результат с провода; `system/permission_denied` и `result.permission_denials` его повторяют и молчат                                              | `is_error`-результат в записи                |
| сабагент                                   | его запись                                           | его запись; повтор вызова родителя в начале записи форка пропускается                                                                                    | его запись                                   |

`rate_limit_event` `rejected` своего события не даёт: стену говорит ошибка API
отказанного хода. Своего producer'а отказов у holder'а нет — это цикл HITL:
замер HATS-2029 показал, что запись несёт только `is_error`-результат, а провод
повторяет его в `system/permission_denied` и `permission_denials`. Каждый журнал,
который оставляет e2e, проверяется на факт, записанный дважды
(`tests/e2e/_helpers/one_producer.py`).

**Порядок — по построению** (поправка HATS-2028). В записи claude нет строки
«ответ кончился» и строки «ход кончился». Ридер записи закрывает ответ, только
когда начинается следующий, приходит маркер interrupt или вызван `close()`
(замер: 24 хода из 25, [1], §10). Кроме того, запись пишется пачками на 0,1–0,4 с
позже провода. Пока содержимое хода шло из записи, а конец хода — с провода,
порядок журнала держался на замерах. Теперь оба факта приходят из одного потока:

- ответ закрывает `message_delta` провода — в ней итоговые `usage` и `stop_reason`;
  все фрагменты ответа приходят раньше неё;
- ход закрывает `result`; если к нему ответ ещё открыт, `result` сначала
  закрывает ответ с итогом `unknown`;
- все строки holder'а — события провода, записи сабагентов и отказы — идут через
  один писатель, а `run_ended` — его последняя строка. Запись после неё писатель
  отклоняет и сообщает в трассу сессии.

Вердикты гейтов пишет диспетчер хуков, мимо писателя. После `run_ended` их нет,
потому что holder закрывает сервер хуков раньше, чем писатель пишет `run_ended`.

### D5 — процесс `ai-hats headless` и есть holder; он планирует сессию и уходит последним

Второго процесса нет. Тот, кто выполнил `ai-hats headless`, планирует сессию
(`SessionRun.create → plan_session → apply → захват → launch → init_audit`),
держит бинарь и живёт ровно столько, сколько сессия. Якорь liveness
(`.session-owner.json`) поэтому называет его pid, а pid ребёнка ложится рядом
(`_claim_surface_child`) — с сырым бинарём он известен.

Holder — третий раннер рядом с `WrapRunner` и `SubAgentRunner`. Под политикой
HITL он наследует обязанности первого, которые `RunMode` сам по себе не даёт:
`serve_hooks` (резидентный `HookServer`), `start_event_log`,
`_claim_surface_child`, finalize. Пайплайн у него свой —
`headless.yaml` с тем же шагом `provider`: сегодняшний шов различает раннеры
одним флагом `interactive`, и третий в него не помещается. Раннер поэтому
выбирается типом параметров запуска (`Headless` — подтип `Hitl`), а шаг
`provider` ветвится по нему.

Порядок конца — ради которого процесс вообще можно считать сигналом: ребёнок
выходит → EventLogWriter дренирует запись и пишет `run_ended` → holder
копирует хвост журнала в stdout → `finalize-headless` (`make_audit`,
`compute_usage`, `run_session_end`) → holder закрывает stdout → `exit`.
Спавна ретро в headless пока нет (решение супервизора, HATS-2020): это
`finalize-hitl` без `maybe_spawn_session_reviewer` и `quorum_autoclose`, а
вопрос, когда headless-сессии нужно ретро, решает HATS-2027. **Holder
уходит последним**, поэтому следить надо за ним, а не за бинарём: бинарь
выходит первым, когда запись ещё не собрана.

Ребёнок спавнится в своей группе процессов (`start_new_session=True`): Ctrl-C в
терминале приходит только holder'у, и тот сам решает, что делать с ребёнком
(D11). Смерть ребёнка — конец сессии тем же порядком. Смерть holder'а —
ребёнок получает EOF на stdin и выходит сам.

stdout принадлежит машине: баннеры старта и конца, напоминание о ретро и
startup-заметки уходят в stderr. Три печатника пишут в stdout сегодня —
`_print_session_start`, `_print_session_end` и шаг `run_session_end`; их
перевод — работа HATS-2020. Если читатель stdout ушёл (`EPIPE`), holder
перестаёт копировать и работает дальше: журнал полон, а конец сессии
определяет stdin и сигналы, не stdout.

### D6 — две независимые оси: кто отвечает за сессию и есть ли у неё канал

Чем headless отличается от того, как мы запускаем ретро: **ничем по части TTY
и вывода — и всем по части канала**. Ретро, triage гипотез и intake идут через
`ai-hats agent`: один промпт из argv, процесс ждёт исхода, второго хода не
будет. Headless-сессия принимает команды, пока открыт её stdin.

|                                          | канала нет (один промпт, процесс ждёт исход)  | канал есть (сессия принимает команды)                                  |
| ---------------------------------------- | --------------------------------------------- | ---------------------------------------------------------------------- |
| **отвечает человек** (политика HITL)     | —                                             | `ai-hats` (канал — PTY), **`ai-hats headless`** (канал — stdin/stdout) |
| **отвечает харнесс** (политика Automate) | `ai-hats agent` — ретро, judge-фаза-1, intake | `ai-hats agent --api` — вне этого ADR (D8)                             |

Политика — существующий тип (`Hitl` / `Automate`, ADR-0005 D2) и существующий
`RunMode`. Он решает три вещи: планируется ли consent (`plan_consent`), гасятся
ли ack-флаги ребёнку (`withheld_from_child`) и какую форму принимает план
surface'а (argv с `--system-prompt-file` / `--plugin-dir` / `--settings` — против
preset-append и option-документа SDK). Worktree, резидентный `HookServer` и
finalize-пайплайн решает **раннер**, поэтому holder берёт их на себя явно (D5).
**Третьего `RunMode` нет**: канал не меняет ни одного режимного решения.

| Ось                      | `ai-hats`               | `ai-hats headless`                             | `ai-hats agent`                                                     |
| ------------------------ | ----------------------- | ---------------------------------------------- | ------------------------------------------------------------------- |
| Политика (`RunMode`)     | HITL                    | HITL                                           | AUTOMATE                                                            |
| Дорога планирования      | argv                    | argv + флаги stream-json (замерено — [1], §10) | argv + флаги stream-json (после HATS-2022; до него — `sdk_options`) |
| Раннер                   | `WrapRunner` + PTY      | holder = сам процесс команды                   | `SubAgentRunner`                                                    |
| Вход                     | терминал                | stdin, один писатель                           | промпт из argv                                                      |
| Выход                    | терминал                | stdout: заголовок + журнал                     | `--json`-конверт в конце                                            |
| Время жизни              | пока человек не выйдет  | пока открыт stdin (или сигнал)                 | один ход                                                            |
| Consent планируется      | да                      | да                                             | нет                                                                 |
| Ack-флаги ребёнку        | наследуются             | наследуются                                    | гасятся                                                             |
| Worktree автоматически   | нет (`rack transition`) | нет                                            | да (`IsolationMode` раннера)                                        |
| Резидентный `HookServer` | да                      | да (holder поднимает сам)                      | нет (гейты спавнятся на вызов)                                      |
| Finalize                 | `finalize-hitl`         | `finalize-headless` (без ретро, HATS-2027)     | `finalize-subagent`                                                 |
| Журнал                   | `events.jsonl`          | `events.jsonl`                                 | `events.jsonl`                                                      |

Наследование ack-флагов у headless — следствие того же тезиса: по политике
headless равен HITL. Известная слабость: обоснование `withheld_from_child`
(«одобрение живёт в той сессии, где его дали») бьёт и по headless-сессии,
запущенной агентом из своего Bash, а headless к такому запуску располагает
сильнее, чем PTY; триггер пересмотра — в D8.

Согласие на вопросы сессии даёт тот, кто владеет её stdin. Замер ([1], §10.1): на
вопрос shared-state гарда роли `answer` allow выполнил `git push --force`. **Так и
задумано** (решение супервизора, 2026-09-24): кто запустил headless-сессию, тот ей
и управляет. Это не независимый сабагент со своими грантами, а сессия, которую
ведёт владелец stdin, и вопросы её гардов адресованы ему. Какие вопросы гардов
доходят до владельца, а какие holder отклоняет сам, задаёт настраиваемая политика
(HATS-2021); по умолчанию доходят все. Настройка нужна, например, автотестам,
которым надо дёргать хуки.

Под политикой HITL у сессии **две** системы разрешений, и на проводе видна одна:
вопрос бинаря приходит как `can_use_tool` и становится `PersonAsked`, а
consent-обёртки, объявленные ролью, спрашивают вне провода и отвечают кодом
возврата — клиент увидит их отказ как результат инструмента. Что с этим делает
headless — предмет HATS-2021. Какой вопрос вообще доходит до провода, решает режим.
Под `auto`, который приходит из пользовательских настроек (HITL-argv их не
срезает), вопрос бинаря почти не появляется. В замере пять действий, включая
`rm -rf` и `curl`, выполнены молча ([1], §10.1). На проводе остаются вопросы
гардов роли: `ask` хука сильнее режима и allow-правил.

Почему `headless` — своя команда, а не флаг `agent`: под флагом у `agent` была
бы мертва половина собственной поверхности (`--task`, `--ticket`,
`--isolation`, ретраи, финальный `--json`-конверт), а один флаг переключал бы
половину строк таблицы. Общий у них движок, а не командная строка.

### D7 — читатель, который не запускал сессию, только читает

Писать в сессию может только владелец её stdin (D2). Любой другой процесс —
статус-панель, аудит, человек, заглянувший в идущую сессию, — читает журнал:
`ai-hats session list` и `ai-hats session show` находят сессию, `tail -f` на
`events.jsonl` даёт живой поток, а жива ли она — видно по якорю liveness (pid
плюс метка старта), как это уже делают свипы. Отдельных глаголов, визитки и
реестра живых headless-сессий нет.

`ai-hats session list` показывает состояние сессии (поправка HATS-2029):

- `ended` — `metrics.json` собран: `finalized: true`, или ключа нет вовсе (запись
  старше заглушки, её писал только finalize);
- `live` — жив хоть один владелец из якоря (holder или ребёнок) с той же меткой
  старта;
- `dead` — не жив никто, или нет каталога кэша: teardown его удаляет, свип —
  когда все владельцы умерли, а якорь пишется раньше `metrics.json`;
- `unknown` — якорь не прочитать.

`session backfill` собирает сессию `dead` — audit и счётчики из записи
surface'а — и не трогает `events.jsonl`: в журнале остаётся ровно то, что
успели записать бинарь и holder, `run_ended` задним числом не появляется, и
`finalized` остаётся `false`. Сессию `live` и `unknown` он не трогает.

### D8 — что решено не делать здесь

- Несколько писателей внутри headless — они садятся сверху: мультиплексор
  владеет stdin/stdout holder'а (так строит свой слой HAI).
- Сокет, сервер, сетевой транспорт — та же причина.
- Сабагент с диалогом — четвёртая клетка таблицы D6 (Automate + канал), здесь
  не строится. Её триггер «родителю нужен второй ход с сабагентом» сработал, и
  форма уже известна — раздел «Сценарий: сабагент с диалогом» ниже; второй
  триггер «ретро переспрашивает вместо холодного перезапуска» имеет замер (66 из
  814 прогонов `session-reviewer`). Строится после HATS-2022, отдельной
  карточкой: ей нужен `ai-hats agent` уже на wire-движке.
- Гашение ack-флагов у вложенного запуска (headless из агентской сессии,
  `AI_HATS_SESSION_ID` уже в среде); пересмотр, когда такой запуск появится в
  реальном сценарии — это ось «вложенность», а не новый `RunMode`.
- `--resume` для headless: у резюмированной сессии сегодня нет журнала
  (`start_event_log` не запускается без `provider_session_id`), значит нет и
  stdout по D2; пересмотр — вместе с журналом для резюма.
- Другие surface'ы — по одной таблице D3 на surface, отдельными карточками.
- Подключение человека к headless-сессии в TUI.
- ACP наружу — адаптер, когда его попросит редактор.
- Свой `--detach` — фон даёт shell.

### D9 — заголовок сессии — первая строка stdout; человеку то же в stderr

```json
{"v":"headless/v1","session_id":"<ai-hats id>","session_dir":"/abs/…/session_<id>","log":"/abs/…/session_<id>/events.jsonl","holder_pid":12345,"provider_session_id":"<uuid>","started_at":"<ISO UTC>","events":"events/v1","commands":["prompt"]}
```

Ключи `session_id` и `session_dir` те же, что в конверте `ai-hats agent --json`.
`events` называет формат журнала, `commands` — команды, которые этот holder
исполняет (поправка HATS-2028): клиент узнаёт, что можно слать, до первой
команды. `v` остаётся `headless/v1` — ключи аддитивны.
Человеку — в stderr:

```text
session  20260921-120000-1-12345
log      /abs/…/session_20260921-120000-1-12345/events.jsonl
input    this process's stdin — one JSON command per line
stop     close stdin (finish and exit) · Ctrl-C or kill -TERM 12345 (abort)
```

Заголовок печатается, когда ребёнок запущен и журнал открыт; сразу за ним идёт
копия журнала с первой строки (`run_started`).

### D10 — данные: канал для ходов, файловая система для объёма, схема для ответа

- **внутрь, мелкое** — текст хода в `prompt`;
- **внутрь, объёмное** — файлом: клиент кладёт файл в рабочую директорию и
  называет путь в промпте, модель читает его своими инструментами. Причина не в
  лимите строки, а в том, что ход остаётся в журнале навсегда и едет в
  контексте каждого следующего хода;
- **наружу, человеку** — события: `ItemEmitted` с текстом, `ToolCallItem` и
  `ToolResultReceived`, `ResponseEnded` с итогом хода;
- **наружу, машине** — структурный ответ от самого бинаря (`--json-schema`), а
  не вырезание маркеров из прозы: форму проверяет бинарь до того, как ответ
  станет строкой записи;
- **ответ на вопрос** — `answer` по `call_id` из `PersonAsked`.

Граница хода для клиента — **`TurnEnded`** (поправка HATS-2020). Holder пишет его на
каждом `result` провода. Журнал идёт в порядке провода (D4), поэтому `TurnEnded`
стоит после всех событий своего хода. Свой `TurnEnded` клиент находит по id
промпта (D3; поправка HATS-2028). Форма — как у `RunEnded`, плюс id:

```json
{"event":"turn_ended","ok":true,"raw_code":"completed","detail":null,"prompt_ids":["<uuid>"],"ts":"…"}
```

- `ok` — `not result.is_error`;
- `raw_code` — слово surface'а, для claude `terminal_reason`, если он есть, иначе
  `subtype`;
- `detail` — текст ошибки при `ok: false`, иначе `null`. Ответ модели уже лежит в
  `ItemEmitted`, и сюда он не копируется;
- `prompt_ids` — id промптов, на которые ответил ход, из `result.user_message_uuids`:
  один у обычного хода, несколько у хода с влитым промптом, ни одного у хода,
  начатого бинарём.

Своё событие понадобилось, потому что ход без ответа модели возможен, и это видно
по коду ридера. Запись claude `isApiErrorMessage` (сбой API, отказ по квоте) даёт
сигнал, а не ответ, то есть ни `ResponseStarted`, ни `ResponseEnded`
(`claude_events.py`, `_assistant_events`). Правило «`ResponseEnded` со
`stop_reason ≠ tool_use` или `completion = cancelled`», которое стояло здесь раньше,
такой ход не видит, и клиент ждал бы вечно. `result` на проводе заканчивает каждый
ход, так что `TurnEnded` полон по построению. Правило по `ResponseEnded` остаётся
верным описанием *ответа*, но клиенту больше не нужно. Consumer живой — клиент
headless (правило D4 ADR-0037), producer один — holder. PTY-ридер мог бы давать то же
событие по `system/turn_duration`; пока его нет, триггер — потребитель в PTY-режиме.

«Моя команда дошла» — это событие, которое она произвела, а не таймаут. Не каждый
ход отвечает на `prompt`: когда завершается фоновая задача, которую запустила
модель, бинарь начинает ход сам ([1], §10), и этот ход тоже кончается `TurnEnded` —
с пустыми `prompt_ids`.

### D11 — конец сессии — это выход holder'а, и у каждого пути свой код

Для владельца stdin ожидание конца — это чтение stdout до EOF и `wait`: EOF
приходит в момент, когда holder закрывает stdout перед выходом (D5), а к этому
моменту журнал закрыт `run_ended` и запись собрана. Двух признаков
отслеживать не нужно — один процесс, один конец.

| Путь                   | Что делает holder                                                                                                                                       | Код                                                  | Запись                                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| EOF на stdin           | отвечает deny на открытый вопрос, закрывает stdin ребёнку; тот доделывает принятые ходы и выходит; `run_ended`; finalize                                | 0                                                    | собрана, все принятые ходы выполнены; вопросы в них отклонены, фоновые задачи остановлены                                                                                               |
| Ctrl-C / SIGTERM       | прерывает: SIGTERM группе ребёнка → grace → SIGKILL; `run_ended`; finalize                                                                              | 130 / 143                                            | собрана; ходы, которые бинарь ещё не начал, не выполнены. Бинарь сам выходит с 143 меньше чем за секунду, убив идущий инструмент; `result` нет, частичный ответ не записан ([1], §10.1) |
| смерть ребёнка         | тот же порядок, что при EOF                                                                                                                             | ненулевой — код ребёнка; смерть от сигнала N — 128+N | собрана                                                                                                                                                                                 |
| SIGKILL holder'у       | ничего — ребёнок получает EOF и выходит сам                                                                                                             | 137                                                  | не собрана: нет `run_ended`, `finalized: false`                                                                                                                                         |
| отказ по readiness     | блокирующая находка пробы (claude не залогинен): holder не проводит логин, surface не запускается, заголовка нет, причина в stderr (поправка HATS-2029) | 1                                                    | каталог сессии есть; в журнале `run_started` → `PersonActionRequired(reauthenticate)` → `run_ended ok=false`; `metrics.json` собран                                                     |
| отказ стартового гейта | гейт старта сессии отказал: surface не запускается, заголовка нет                                                                                       | 3                                                    | каталог и `diagnostics.json` есть, журнала нет, `finalized: false` — путь общий с TUI                                                                                                   |

Строка SIGKILL — единственный путь потери, и родитель узнаёт его по коду. Код
137 даёт и ребёнок, убитый `SIGKILL`; различает их журнал: при смерти ребёнка
`run_ended` есть.
Читатель, который не запускал сессию (D7), узнаёт то же по файлам: holder мёртв
по якорю, а последнее событие журнала — не `run_ended`.

Что гарантирует, что по пути ничего не потеряно:

- событие становится фактом в момент записи: одна строка — один `write(2)` в
  `O_APPEND`-дескриптор, и читатель видит её сразу, как вызов вернулся. Это
  защита от падения процесса, а не от пропажи питания — `fsync` нет, и журнал
  его не обещает;
- рваных строк не бывает ни в stdout, ни у читателя файла: holder копирует и
  читатель читает только байты до последнего `\n`;
- stdout — копия журнала с первого байта, а не параллельный поток, поэтому
  расхождения между тем, что видел родитель, и тем, что записано, быть не может;
- каждая принятая команда оставляет своё событие; после EOF принятые ходы
  дорабатываются до конца, после сигнала — нет, и журнал показывает, какие
  успели.

Чего **не** считать концом: тишину в stdout. Сессия законно молчит, пока модель
думает, инструмент работает или вопрос ждёт `answer`.

Ни один существующий пайплайн не переписывается. Автоматика после сессии целиком
висит на `SubAgentRunner`, а HATS-2022 меняет движок *под* ним — поэтому она
переезжает на провод молча.

**Переносить ли пост-HITL-автоматику на headless — нет.** По политике:
`session-reviewer` — процесс без человека, его клетка — Automate, а headless
принёс бы ему планирование consent, наследование ack-флагов, резидентный
`HookServer` и отсутствие автоматического worktree. По выигрышу: он есть, но
принадлежит **проводу**, а не каналу. Замер на 814 прогонах `session-reviewer` в
этом репозитории: 83% успех, 9% таймаут (exit 124), 8% — ровно 66 прогонов —
«failed validation after 2 attempt(s)», то есть дважды ответ не той формы и
оба раза полный холодный перезапуск (медиана прогона — $0.66). Причина —
вырезание ответа маркерами `BEGIN_REFLECT_SESSION_RETRO` / `END` и разбор YAML;
`--json-schema` на проводе закрывает класс в корне, канал для этого не нужен.
Канал добавил бы меньшее — переспросить в той же сессии вместо холодного
перезапуска; это триггер `agent --api` (D8), и он вступает в силу после
HATS-2022, а не вместо него.

## Как управляется headless-сессия

### Процесс: запустить, посмотреть, остановить

```bash
# из терминала: stdin — клавиатура, stdout — поток событий
ai-hats headless -p claude -r maintainer

# скриптом, все ходы заранее: закрытый stdin = «доделай и выйди»
ai-hats headless -p claude -r maintainer < turns.ndjson > events.ndjson
echo "exit=$?"                        # 0 — все ходы выполнены, запись собрана

# посмотреть идущую сессию со стороны (только чтение, D7)
ai-hats session list
tail -f /abs/…/session_<id>/events.jsonl

# остановить: закрыть stdin (доделать) или прервать
kill -TERM <holder_pid>               # или Ctrl-C в терминале holder'а
```

### Данные: пишем ход, читаем шаги, ждём конца

```bash
coproc H { ai-hats headless -p claude -r maintainer 2>holder.err; }
pid=$H_PID                                          # сразу: bash снимет H_PID, когда coproc выйдет
read -r header <&"${H[0]}"                          # строка 1 — заголовок
echo "$header" | jq -r .log                         # где журнал

id=$(uuidgen | tr '[:upper:]' '[:lower:]')          # канонический UUID — в нижнем регистре
echo "{\"v\":\"commands/v1\",\"cmd\":\"prompt\",\"id\":\"$id\",\"text\":\"прочитай docs/INDEX.md\"}" >&"${H[1]}"
while read -r ev <&"${H[0]}"; do                    # строки 2.. — события
  case "$(jq -r .event <<<"$ev")" in
    person_asked)   # отвечаем по call_id
      cid=$(jq -r .call_id <<<"$ev")
      echo "{\"v\":\"commands/v1\",\"cmd\":\"answer\",\"call_id\":\"$cid\",\"decision\":\"allow\"}" >&"${H[1]}" ;;
    turn_ended)     # ход окончен — если в нём наш промпт
      jq -e --arg id "$id" '.prompt_ids | index($id)' <<<"$ev" >/dev/null && break ;;
  esac
done

exec {H[1]}>&-                                      # «больше ничего не пришлю»
cat <&"${H[0]}" >/dev/null                          # дочитываем хвост до EOF
wait "$pid"; echo "exit=$?"                         # конец: журнал закрыт, запись собрана
```

Ждать конца — значит дочитать stdout до EOF и забрать код; ничего третьего нет.
Несколько клиентов одновременно — это мультиплексор над этим процессом,
держащий его пайпы, а не второй писатель в него.

## Сценарий: сабагент с диалогом (строка 8 матрицы)

Здесь не строится (D8), но форма известна и проверена, поэтому записана — чтобы
карточка, которая её построит, начала с контракта, а не с разведки.

**Почему это не `ai-hats headless`.** Сабагент — отдельная сессия: своё id,
свой каталог, своя композиция. Ровно этим `withheld_from_child` обосновывает,
что гранты родителя ребёнку не достаются. Ему нужны worktree (`--isolation`),
иначе он пишет в checkout родителя, `finalize-subagent`, `--task` и `--ticket`.
Это поверхность `ai-hats agent`, и в этом сценарии она живая — поэтому клетка
Automate + канал, движок тот же, что у holder'а.

**Почему нужен слой сверху.** Агент в Claude Code не может держать пайп между
вызовами Bash: каждый вызов — отдельный shell. Владельцем stdin ребёнка должен
быть кто-то долгоживущий, то есть мультиплексор сверху в самом малом виде:
файл команд, который читает `tail -f`, и его вывод на stdin ребёнка. Проверено
с заглушкой вместо holder'а: строки, дописанные из отдельных shell'ов, приходят
по порядку, а убийство одного `tail` даёт мягкий EOF — ребёнок доделывает
принятые ходы, пишет `run_ended` и выходит чисто.

**Поток.** Человек в HITL-сессии просит агента запустить сабагента, дальше:

1. **Запуск** — один вызов Bash в фоне, с `timeout` как бюджетом сабагента
   (без границы гард command-lifetime запуск не пропустит):
   `( tail -n +1 -f cmds.ndjson & echo $! > feeder.pid; wait ) | ai-hats agent -r X --task "…" <канал> > events.ndjson 2> child.err &`
2. **Заголовок** — первая строка `events.ndjson` (это файл, а не пайп, поэтому
   ловушки с `head` и `EPIPE` здесь нет).
3. **Ожидание хода** — родитель блокируется на `ai-hats wait --until-cmd`
   с предикатом «появилось новое `turn_ended` или `person_asked` после моего
   смещения»; контракт 0 / 124 / 2 уже есть. Claude Code будит родителя только
   на выходе процесса, поэтому между ходами родитель ждёт — как сегодня ждёт
   `ai-hats agent`.
4. **Ветвление.** На `person_asked` родитель отвечает сам **или несёт вопрос
   человеку** («сабагент просит Write в X — разрешить?») и дописывает `answer`
   в `cmds.ndjson`. На `turn_ended` забирает результат через `jq`, не
   читая журнал целиком, и либо дописывает следующий `prompt` («не то,
   переделай Y»), либо заканчивает.
5. **Конец** — `kill $(cat feeder.pid)`: EOF, ребёнок доделывает принятые ходы,
   `run_ended`, finalize, выход; Claude Code будит родителя с кодом выхода.

**Выигрыш против сегодняшнего `ai-hats agent`:** второй ход на тёплом
контексте вместо холодного перезапуска; вопросы ребёнка о разрешениях доходят до
родителя и через него до человека (сегодня Automate-сабагент не спрашивает
никого); прогресс виден по ходу, а не только финальным конвертом.

**Ловушки, найденные проверкой.** `pgrep -f` по строке `tail` находит и
форкнутый bash фильтра — его argv содержит ту же строку; убить оба значит
прервать ребёнка, а не закончить его: `run_ended` не появится. Поэтому feeder
записывает свой pid сам. Предикат `wait` должен считать новое после смещения,
а не «есть ли вообще»: иначе он сработает на первом же ходе навсегда. Раз эту
ошибку легко сделать в shell, строить стоит флаг — адаптер, которым CLI сам
держит `tail` и его pid, — а не документировать голый рецепт. Флаг живёт перед
движком holder'а, и тот по-прежнему видит только stdin: правило «сверху, а не
внутрь» не нарушается.

## Следствия

- HATS-2020 строит wire-движок и `ai-hats headless` как третий раннер: пайплайн
  `headless.yaml`, команды D3, копирование журнала в stdout, порядок конца из D5
  и коды из D11, перевод трёх stdout-печатников на stderr. HITL-argv поверх
  stream-json и `interrupt` замерены до него ([1], §10). В первом трассере — граница
  хода по `result` (D4) и проверка правила D10 на четырёх концовках хода.
- HATS-2021 закрывает режимы разрешений (policy-only / клиент отвечает / гейты
  через `settings.json`), вторую систему разрешений (consent-обёртки с кодом
  возврата), таймаут ожидания `answer` и настраиваемую политику: какие вопросы
  гардов доходят до владельца stdin (D6).
- HATS-2022 переводит `ai-hats agent` на тот же wire-движок; с SDK-движком
  уходит ветка AUTOMATE в `launch()`, `Launch` сужается до argv — ADR-0036 D4
  сужается. Ретро, judge-фаза-1 и intake переезжают без правок пайплайнов.
  Сигналы квоты переезжают из SDK-потока на провод (D4): предупреждение —
  `rate_limit_event`, стена — ошибка API отказанного хода.
- HATS-2028 делает провод единственным источником событий основного агента в
  headless (D4), переносит формат claude в кодек surface'а в обе стороны, а
  словарь команд — в `ai_hats_observe` (D3), и атрибутирует ходы по id промпта
  (D3, D10). После неё контракт ядра для клиента замораживается — точка go 1 HAI.
- HATS-2029 сводит каждый факт к одному producer'у во всех режимах (D4), даёт
  `session list` состояние по якорю, а `session backfill` — сессию, убитую без
  finalize (D7), и отказывает незалогиненному claude до старта (D11).
- `events.jsonl` не меняется по формату. Видов записей становится на один больше —
  `turn_ended` (D10), полей — на два (`prompt_id`, `prompt_ids`), и всё это
  аддитивно, `events/v1` не бампится. В `WorthRecording` появляется одна причина —
  `command_rejected`.
- Сабагент с диалогом (строка 8 матрицы) — отдельная карточка после HATS-2022;
  её контракт — раздел «Сценарий» выше.
- `RunMode` не растёт; ADR-0005 не меняется.

## Не входит в решение

- Поток токенов (`ItemDelta` из `content_block_delta`). `--include-partial-messages`
  holder включает ради итоговых `usage` и `stop_reason` (D3), а сами частичные
  сообщения в журнал не пишет. Триггер — клиент, которому нужен поток токенов.
- Гарантии порядка для сабагентов (D4). Триггер — HAI нужен вид сабагента.
- Событие «промпт в очереди» из `command_lifecycle queued`. Триггер — HAI нужен
  индикатор ожидания; событие аддитивно.
