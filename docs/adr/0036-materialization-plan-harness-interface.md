# ADR-0036: План материализации — интерфейс харнеса и его получение из обоих DSL

## Статус

Предложен (HATS-1962, 2026-09-13; ревизия того же дня вслед за ADR-0034 [2]:
имена плана — полные пути, `run` — путь payload, `EXECUTABLE` снят; ревизия
2026-09-15 по итогам шага 1 HATS-1971 — интерфейс в коде, `surfaces/plan.py`:
D1–D3, D5–D7 и D9 приведены к его форме; ревизия 2026-09-16 по итогам шага 2 —
первый планировщик, claude: входы `layout` и `host`, `document` / `on_path` у
скилла, типы пары запуска, форма записи — D1, D2, D4–D6). Часть серии плоской модели: обзор и
слои — ADR-0033 [1]; что пишет автор — ADR-0034 [2]; как это вычисляется —
ADR-0035 [3]. Статус меняется на «Принят» вместе с ADR-0033. Исполняется
карточкой HATS-1971 как **пререквизит** первого этапа.

Документ описывает **слой плана** и границу с **слоем харнесса**: что именно
получает харнесс, откуда это значение берётся для сегодняшнего DSL и для
нового, и почему оба берутся одинаково.

## Контекст: что харнесс получает сегодня

Списано с кода (замер 2026-09-12 на карточке HATS-1971).

**План уже значение и уже наполовину готов.** `MaterializationPlan`
(`src/ai_hats/materialization.py`) — список `MaterializationEntry`; запись —
frozen dataclass `kind / target / size / source / file_count / detail /
digest`, где `kind` — один из `write_text`, `write_executable`, `copy_tree`,
`symlink`, `merge_json`, `remove_tree`, `mkdir`. Накапливают его **оба**
порта: `ApplyMaterializer` пишет и записывает, `PlanMaterializer` записывает и
не трогает ничего. Потребителей четыре: `dry_run.py`, `subagent_runner.py`,
`session_report.py` и через него запись сессии.

**Запись запуска уже есть.** `SessionReport` (`src/ai_hats/session_report.py`)
— то, что уезжает в `role_materialization.json` сессии: `role` (строка
выражения), `provider`, `run_mode`, `policy`, `launch` (argv), `env` (что
ai-hats добавляет окружению), `prompt` (путь), `prompt_text`, `plan`, `cwd`,
`escapes`, `notes`, `checks`, `consent`. Его читают `safety-guard` (точки
консента) и `consent_port.py` (обёртка).

**Поверхность получает категории.** `ArtifactCategory` — `CONTEXT`, `SKILLS`,
`HOOKS`, `SETTINGS`; поверхность реализует `_build_<категория>_<режим>` (ADR-0018
[4]), и `build_session_artifacts` обходит категории по `SessionPolicy`. Что
каждая поверхность получает на выходе:

| Поверхность | Context                                       | Skills                          | Hooks                                       |
| ----------- | --------------------------------------------- | ------------------------------- | ------------------------------------------- |
| claude      | `--system-prompt-file <cache>/prompt.md`      | `--plugin-dir <cache>/plugin`   | `--settings <cache>/settings.json`          |
| agy         | `--add-dir <cache>/rules` (`rules/GEMINI.md`) | `<cache>/rules/.agents/skills/` | `<cache>/hooks.json` + глобальный диспетчер |
| cline       | `--config <cache>`                            | `<cache>/skills`                | `<cache>`                                   |

**Чего не хватает до сравнимости** — пять вещей:

1. **Пути абсолютные.** `target` несёт идентификатор сессии и корень кеша:
   два прогона расходятся на ста процентах записей, и это правда про пути, а
   не про поведение.
2. **Планирование читает ФС.** `describe_copy_tree` обходит `src.rglob` и
   считает `dir_digest`; `describe_write_text` и `describe_merge_json` читают
   текущий файл; `PlanMaterializer._would_exist` зовёт `path.exists()`;
   `executable_at` реализован трижды и каждый раз читает диск.
3. **Идемпотентность не требуется, а наблюдается.** `duplicates()` существует,
   чтобы найти «те же байты произведены дважды», и единственный его
   потребитель — строка в отчёте.
4. **Эффект ветвит планирование.** `merge_json` возвращает «изменилось ли»;
   оба вызова результат выбрасывают, а сама проверка читает пользовательский
   `settings.json` во время планирования.
5. **Выход смешивает три природы.** `BuiltArtifacts` несёт эффекты на файлы
   (план — боковым каналом через `port`), параметры запуска (`cli_args`,
   `extra_env`, `sdk_options`, `full_content`) и сантехнику (`port`, `policy`,
   `resources`, `notices`); `policy` и `port` — входы, приехавшие в объекте
   выхода; поверхности дописывают харнесс-специфику в общий конверт (cline
   кладёт `-s`, `--config`, `--hooks-dir`).

**Два производителя промпта.** `config show-prompt` зовёт
`provider.build_system_prompt(result)` напрямую, мимо материализации;
саб-агент идёт через `build_session_artifacts`. Тексты совпадают только
потому, что оба пути утыкаются в `compose_sections` — совпадение реализации,
не контракт. Инцидент HATS-1552 — ровно этот класс: у dry-run была своя
версия сборки, и сообщённая команда не была командой.

## Решения

### D1 — План — одно значение из двух половин

План — frozen-значение, сравнимое оператором `==`; у каждой записи вниз по
дереву есть `digest`, складывающий дочерние, так что дайджест плана меняется
от любого байта, за который план отвечает, и ничто добавленное в план не
выпадает из хеша по забывчивости. Две половины, потому что у них два
производителя:

**Композиционная половина** — нейтральна к поверхности, производит процессинг
[3]:

```
identity      каноническая строка выражения (или имя композита)
prompt        { blocks: [ { name | None, members: [ { name, text, heading? } ] } ] }
              # text — байты, которые читает агент: плейсхолдеры и каталог ролей
              # развёрнуты для layout; рендер (## <NAME>, ### <heading>) — свойство значения
skills        [ { name, path, content_digest, document?, on_path } ]
              # путь абсолютный; одно дерево в двух местах — два скилла
              # document — SKILL.md, как его читает агент (плейсхолдеры и таблица рёбер FSM
              #   развёрнуты для layout); on_path — подкаталоги, чьё содержимое агент зовёт
              #   по имени (scripts, bin) — только те, что в дереве есть
hooks
  runtime     [ { at: HookEvent, matcher, run: Executable } ]       # единственная строка, которую вяжет поверхность
  external    [ { app, object?, at, run?: Executable, on_error?, declared_by } ]
              # git | rack | wt | consent_gate — читает интеграция зависимости из записи, не поверхность
trace         [ { term, brought_by, removed_by? } ]      # трасса разворачивания; brought_by — композит или override
```

`Executable` — `{ path, content_digest }`, путь абсолютный; зеркальный адрес
скрипта в сессии — производная `home_of(run, skills)`, не поле. `at`
runtime-хука — закрытое множество канала хуков (ADR-0020), не написание
поверхности; `matcher` — в matcher-словаре канала, на который каждая
поверхность отображает свои имена инструментов. `name` всюду — полное имя по
ADR-0034 [2] D1: путь от корня слоя через `::`, никогда суффикс, которым терм
был записан.

Консент — внешний хук `{ app: consent_gate, object: <операция>, at: <селектор>,
run: None }`: концов `from`/`to` в значении **нет** — иначе процессинг обязан
знать грамматику селектора rack; их пишет проекция записи парсером владельца
операции, потому что хук stdlib-only и парсер импортировать не может (ADR-0027
D2). Точка консента **вооружена ⇔ она есть в `hooks.external`**; снятая точка —
факт трассы (ADR-0035 [3] D7), в хуках её нет, читатели политики —
`safety-guard`, обёртка — видят только вооружённые.

Диагностика — **не** в плане: план несёт только то, что материализуется.
Находки адаптера (объявленный скрипт отсутствует, терм никем не объявлен) идут
в тот же sink, что и собственные находки композитора — в payload, в заметки
dry-run, в stderr `show-prompt`.

Воронка ADR-0005 §3 [5] — контракт между процессингом и планом: отсутствующее
значение — `None` или отсутствие ключа (`heading?`, `object?`, `run?`,
`removed_by?`), никогда `""`, `[]` или `0`, которые суть значения; безымянный
блок промпта — `name: None`, не `""`.

**Эффектная половина** — специфична поверхности, производит **планировщик
поверхности** (**D2**):

```
prompt        { blocks }   # блоки композиции, затем блоки поверхности (индекс скиллов,
                           # harness-секция); context-запись или argv-токен несут prompt.text
surface       claude | codex | opencode | cline | agy
run_mode      hitl | automate
policy        { context, hooks, settings }
root          <корень сессии — ВХОД планирования; все пути в плане абсолютные>
entries       [ { kind, target, content? | data? | source?, private?, escape?, tree_digest? } ]
env           { KEY: value }                              # что ai-hats добавляет окружению
launch        { args: [...] } | { sdk_options: {...} }   # ровно одно из двух
```

Запись — инструкция, не протокол: она несёт то, что пишет, и `apply` без неё
не нуждается ни в чём. Восемь видов — `write_text` и `write_executable`
(`content`); `copy_tree` (`source` + `tree_digest` — дайджест дерева, **вход**,
посчитанный стадией разбора); `copy_file` (`source` — один файл вне плана,
креденшел в доме пользователя, байты читает применение; единственный вид
кроме `write_text`, который может быть `private`); `symlink` (`source`);
`merge_json` (`data` — то, что ai-hats **добавляет** к документу; слияние — на
применении, **D3**); `remove_tree`; `mkdir`. `digest` и `size` записи —
производные от байтов в руках, не поля: запись не может заявить байты,
которых не держит. `escape: true` — цель вне `root`, объявленная
планировщиком (глобальный `settings.json` agy). Категории `CONTEXT / SKILLS /
HOOKS / SETTINGS` остаются группировкой записей; типы [2] ложатся на них один
в один.

Что **уходит** из выхода: `port`, `policy` как выход, `resources`,
`materialized` (слабый дубликат `entries`), `notices` как отдельное поле,
`file_count` и `detail` (факты применения — они в исходе, **D3**). Что **не**
покрывается никогда: приватные записи идут без `digest` намеренно — ни в
записи, ни в дайджесте плана, — и содержимое приватных файлов сравнением не
проверяется; это названо, чтобы сравнение не выглядело полнее, чем оно есть.

### D2 — Планирование: чистая функция от входов, без чтения диска

```
plan(composition, surface, run_mode, policy, root, layout, host) -> Plan
```

Корень сессии — **вход**: иначе цели не абсолютны, а два планирования для
одного корня — единственное, что сравнивают, — не равны. Идентификатор сессии
и корень кеша входят через него; больше ничего из адресации планирование не
знает. Два входа сверх адресации сессии: `layout` — адресация проекта (корень,
`.agent`), значение; `host` — факты машины, которые планирование не читает:
интерпретатор, под которым идут хуки, обёртки и сервер форм, `PATH`, который
наследует дитя, и где стоит каждая команда, которую умеет оборачивать реестр
консента. Их снимает стадия до планирования (`probe_host`) — как перечисление
дома ниже; без этого `which` и `sys.executable` читались бы внутри сборки.

Планирование **не читает файловую систему**: ни `rglob`, ни `read_text`, ни
`exists`. Всё, что раньше решалось чтением диска — `executable_at`,
`_would_exist`, «изменился ли файл», дайджест дерева, — либо переезжает на
применение (**D3**), либо становится входом. **Входы читает стадия до
`plan()`**, и их два рода: библиотеку читает адаптер (**D7**) или процессинг
(**D8**) — payload хука, дайджест дерева скилла; дом пользователя читает
перечисление конфиг-дома поверхности (`~/.config/opencode`, `~/.codex`) —
план перечисляет каждую ссылку, запись показывает её и помечает источник вне
композиции. Байты, которых у планировщика нет — документ пользователя под
`merge_json`, креденшел под `copy_file`, — читает применение. Дайджест записи
считается по байтам в руках (текст промпта, файл хука из библиотеки), а не по
тому, что лежит на диске сессии.

Планировщик поверхности — это сегодняшние `_build_<категория>_<режим>`,
переписанные так, чтобы **возвращать записи**, а не звать порт: поверхность
переводит композиционную половину в эффекты и параметры запуска для себя и
ничего не дописывает в общий конверт; свой промпт она собирает из блоков
композиции и своих блоков (**D1**, `prompt` эффектной половины). Консент она
переводит так же: из внешних хуков `consent_gate` строит обёртку бинаря —
сегодняшний `consent_wrapper`; концы `from`/`to` разбирает планировщик
консента адаптером операции. Отказы на планировании, не строки в отчёте:
дубликат целей в `entries` (в любом написании) и цель вне корня без `escape` —
функции над планом (`validate`); селектор консента, который адаптер операции
не разбирает, — сегодняшний отказ обёртки *«invalid selector»* — отказ
планировщика консента: план грамматики селектора не знает.

На время миграции планировщик стоит **рядом** со сборщиком: поверхность,
переопределившая `Surface.plan`, идёт путём плана; у которой его нет — старым
путём через порт. Предикат один — `plans(surface)`; на нём ветвятся раннеры,
`--dry-run-experimental` и `show-prompt`. Первая — claude.

### D3 — Применение: механическое и идемпотентное

```
apply(plan) -> Applied
```

Применение делает ровно то, что написано в `entries`, в их порядке. Оно
**идемпотентно**: применить дважды равно применить один раз; применить к уже
материализованной сессии — не сделать ничего. Решение «не писать, если не
поменялось» — свойство применения, не планирования: `merge_json` перестаёт
возвращать «изменилось ли».

До первой записи проверяется каждый источник: дерево — по дайджесту, файл под
`copy_file` — что он есть, цель `merge_json` — что там JSON-объект
(`StalePlan`, `UnmergeableTarget`; ничего не тронуто). Дерево синкается так,
как его писал бы `copytree` — все каталоги, симлинки раскрыты, лишнее снято;
файл внутри, который пишет **более поздняя** запись, остаётся ей. `merge_json`
сливает `data` с текущим документом: объекты — по ключам, списки — по
managed-тегу `_ai_hats_managed` (управляемые элементы заменяются как
множество, чужие сохраняются), остальное — целиком; чужой ключ в файле
пользователя не стирается никогда. Ссылка или каталог на месте файла уступают,
сквозь них не пишут; `remove_tree` — «обеспечить отсутствие».

Исход применения — значение `Applied`: по записи `written | unchanged |
removed | absent` и факты применения (число файлов дерева — то, что ушло из
записи в **D1**). Его читают запись сессии (**D6**) и заметка
`--dry-run --materialize`; тесты идемпотентности считают сверх него примитивы
файловой системы.

Харнесс-нейтральность: применение знает восемь видов эффектов и ничего о
харнессе. Каким флагом сказать харнессу о применённом — вопрос `launch`, а его
поверхность построила на планировании (**D2**).

### D4 — Запуск: пара (план, флаги запуска)

```
launch(plan, flags) -> session
```

Харнесс инициализируется парой. **Флаги запуска** — то, что не меняет план, а
меняет, как поверхность его применяет и вызывает: HITL или Automate,
изоляция, дополнительные аргументы, канал согласия. Разделение HITL/Automate
из ADR-0005 D2 [5] живёт здесь — в `run_mode` на входе планирования и в
флагах запуска, — а не в материализации: у одного выражения один план на
режим, и никакого канала переопределения промпта у `WrapRunner` нет.

Аргументы вызова поверхность строит **из** `plan.launch` и `plan.env`; ничего
не собирается в момент запуска повторно. Это то, чего требовал HATS-1211 R8
(«один сборщик argv») и не дожал HATS-1552: сообщённая команда — это команда.

Пара в коде — `LaunchFlags` и `Launched`. Флаги: идентификатор сессии и
каталог её записи (откуда гейт читает план обратно), путь трассы и pid корня
(в отчёте — *assigned at launch*), собственный идентификатор харнеса или
`None`, когда его чеканит харнесс (запись саб-агента называет этот слот
плейсхолдером — она пишется до чеканки); аргументы
оператора; рабочий каталог; модель; **brief** саб-агента — текст первого хода
(TICKET_CONTEXT / LINKED_CONTEXT / TASK), который собирает вызывающий,
владеющий id карточки, — так `launch` не знает трекера; и брать ли ресурсы
по-настоящему. Ответ — `Launched`: argv или документ опций SDK (ровно одно),
окружение, которое добавляет ai-hats (`plan.env`, затем identity сессии и
флаги), и байты, которые получает агент. HITL-argv собирается одинаково для
всех поверхностей; запуск саб-агента — `Surface.automate_launch`: у
CLI-поверхности argv с мета-промптом из контекста, WORKING_DIRECTORY и brief,
у SDK-поверхности — документ опций от `plan.launch.sdk_options`, окружения
и флагов. Как запись называет запуск — `Surface.describe_launch`: argv, у
SDK — `k=v` против дефолтов.

### D5 — `dry-run` и `show-prompt` — проекции плана

Оба стоят **после** плана и ничего не производят:

- `dry-run` рендерит план целиком — обе половины плюс параметры запуска; с
  `--json` — как значение. Это то, чем видно хуки и точки консента, которые в
  промпте не показываются вовсе; ровно этой слепоты стоил HATS-1955.
- `show-prompt` печатает `prompt.text` — и ничего больше: для поверхности —
  `MaterializationPlan.prompt.text` (блоки композиции и блоки поверхности),
  без поверхности — текст композиционной половины; в обоих случаях
  плейсхолдеры развёрнуты, это то, что читает агент.

Второго сборщика нет по построению: проекция читает значение, которое уже
сравнили (**D9**). Предпросмотр **без сессии** возможен именно потому, что
планирование свободно от диска (**D2**): корень — вход, и предпросмотр
планирует для корня-заглушки. Пока живёт старый путь, проекция плана —
`--dry-run-experimental` (те же модификаторы `--dry-run-json`,
`--dry-run-full`, `--materialize`; поверхность без планировщика отказывает и
называет `--dry-run`); `show-prompt --provider` печатает `plan.prompt.text`
у поверхности, которая планирует, и композиционный текст у остальных.

### D6 — План — запись сессии, и вход рефлексивного контура

План кладётся в артефакты сессии **через инфраструктуру аудита**:
`Session.init_audit` получает план на месте сегодняшнего снимка композиции —
не как побочный эффект стадии планирования и не как значение `produces` для
маршрутизации; это ADR-0005 §4 [5]. Границу пакетов план пересекает как своя
запись: `session_record` проецирует план, пару запуска и исход применения
(**D3**) в одну dict — `role_materialization.json` — и `init_audit` берёт её
композиционную часть, те же байты. Ключи записи, у которых есть читатели:
`role`, `provider`, `run_mode`, `policy`, `launch`, `env_keys`, `prompt`,
`materialized` (с `outcome` и числом файлов, когда применение было),
`consent`, `composition`. Читатели консента — `safety-guard`,
`consent_port.py` — читают точки из той же записи, что и сегодня: `consent[]`
— проекция внешних хуков `consent_gate` с концами `from`/`to`, которые пишет
парсер владельца операции (**D1**); снятой точки в хуках нет, так что запись
несёт только вооружённые.

Рефлексивный контур читает план: аудит сессии — `hooks`, `consent`, `trace`
вместо провенанса ролей и трейтов; `reflect role` — план выражения
(`ai-hats -re dry-run "<expr>" --json`) вместо слоистого экспорта
`role-injection.md` / `traits/<имя>.md`; факты session-reviewer — из того же
значения. Карта контура `docs/reflect.md` [6] обновляется на этапе
верификации (ADR-0033 [1], этап 2).

### D7 — Как план получается из сегодняшнего DSL

Сегодняшний путь меняется **только в хвосте**, и это работа HATS-1971:

```
roles/ traits/ rules/ + customizations ─▶ композитор ─▶ CompositionResult
    ─▶ адаптер ─▶ композиционная половина (D1) ─▶ планировщик поверхности (D2) ─▶ Plan
```

- Композитор и его правила **не трогаются**: `CompositionResult` с
  `trait_injections`, `role_injection`, `rules`, `skills`, `checks`,
  `consent` остаётся внутренним значением старого процессинга.
- **Адаптер** переводит его в композиционную половину: секции
  `compose_sections` становятся блоками с членами (безымянный блок для
  инъекций, `PRIORITIES`, `RULES` с заголовками), текст члена развёрнут для
  `layout`, рендер — у плана; runtime-канал frontmatter → `hooks.runtime`;
  `checks`, git- и worktree-каналы frontmatter и `consent` → `hooks.external`
  по одной строке на точку; трасса — по конфигам трейтов и провенансу
  оверлеев. Имена адаптер пишет в форме нового DSL по таблице миграции [2] D6
  — `maintainer::prompt`, `rules::rule_backlog_discipline`,
  `skills::quality-gate` — иначе `==` расходится на каждом имени, и
  сравнение (**D9**) мерит нотацию, а не модель.
- **Планировщик поверхности** — общий с новым путём (**D2**): один код,
  один вход.

`BuiltArtifacts` расщепляется на план и запуск; порты становятся `apply`
(**D3**). Поведение сессии не меняется — меняется контракт; приёмка HATS-1971
это и держит: существующий прогон зелёный, план двух прогонов с разными
идентификаторами сессии равен по `==`, планирование на пустом каталоге даёт
тот же план, что на материализованной сессии, повторное применение не
производит ни одной записи (с позитивным контролем — изменённый вход
производит).

### D8 — Как план получается из нового DSL

```
experimental/ (composite + override) + выражение ─▶ процессинг [3] ─▶ композиционная половина (D1)
    ─▶ планировщик поверхности (D2) ─▶ Plan
```

Новый процессинг отдаёт композиционную половину напрямую — адаптера нет,
потому что нет промежуточного значения на снятом словаре. Планировщик
поверхности — **тот же**, что в **D7**. Всё, что различает два пути, лежит
левее композиционной половины; всё правее — общее.

### D9 — Сравнение: `==` над планами, объявленные расхождения — вход

Критерий готовности кандидата (ADR-0033 [1], этап 2): для каждого композита
корпуса и каждой поверхности

```
plan(-r, X, surface) == plan(-re, X, surface)
```

Оракул не заводится: оракул — это оператор `==` над планом при условии, что
план чист и применение идемпотентно (**D2**, **D3**); поэтому HATS-1971 —
пререквизит, а не улучшение. Внутренние значения процессингов
(`CompositionResult` и что бы ни было у нового) в критерий **не входят**.

**Объявленные расхождения — вход сравнения, а не комментарий к выводу.** Файл
объявлений: имя композита, запись плана, причина. Необъявленное расхождение
красное всегда. Одно объявлено уже здесь и на весь корпус: `prompt.text`
после смены порядка блоков [3] отличается на каждом композите. Для него
сравнение слабее и названо: по объявленному расхождению сравниваются
**множества** членов `prompt` (имя, текст, заголовок), по необъявленному —
байты. Это единственное место, где сравнение не есть `==`, и оно названо,
чтобы не разрастись.

Отсюда условие снятия старого пути: «кандидат выдаёт то же, что эталон»
означает «не даёт расхождений сверх объявленных».

### D10 — Направление, не приёмка: план, нейтральный к поверхности

В идеале эффектная половина для разных поверхностей должна совпадать, а
различия — уезжать в `launch`. Сегодня это далеко не так: у поверхностей
разные файлы настроек, каталоги и флаги (таблица в Контексте). Записано целью,
а не приёмкой: план по **D1** уже разделяет «что» и «куда», и это делает
сближение возможным без второго контракта.

ADR-0026 [7] (предложен, не принят) отдаёт схему плана материализации и его
миграции способности C3 и проводит границу «до сессии / сессией» в D13; это
решение с ним согласно и на него не опирается.

## Последствия

- Один контракт на вход харнесса для обоих DSL: сравнение двух систем — `==`
  над одним значением, без нормализатора, которому надо доверять.
- `show-prompt` и `dry-run` перестают быть сборщиками; второй производитель
  промпта исчезает по построению.
- `role_materialization.json` и снимок композиции сливаются в одну запись —
  план плюс флаги; читатели консента не меняют источник, меняется его форма.
- Планирование без ФС делает предпросмотр без сессии возможным, а два прогона
  для одного корня — сравнимыми; цена — входы читает стадия до планирования,
  байты вне плана читает применение, дайджесты — по байтам в руках, а не по
  диску, и приватные записи без дайджеста вовсе.
- Идемпотентность применения становится требованием с тестом, а не
  наблюдением в отчёте; исход применения — значение, а не чтение диска.
- HATS-1971 остаётся пререквизитом первого этапа; его приёмка — приёмка
  **D2**, **D3**, **D7**.

## Не входит в решение

- Правила, по которым композиционная половина вычисляется, — ADR-0035 [3].
- Форма файлов и конфигов — ADR-0034 [2].
- Секции промпта, зависящие от харнесса, — следующий ADR; план для них уже
  готов (`prompt` — запись, не сборка), решение — нет.
- Сближение эффектных половин между поверхностями (**D10**) — направление.
- Энфорсмент консента (обёртка, `safety-guard`) — не меняется; меняется форма
  записи, которую он читает (**D6**).
